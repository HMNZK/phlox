# ADR 0031: 本文の折り返しはテーマで、表は幅を見積もって横スクロールで読ませる

> **このファイルの役割**: モバイルのチャット本文が「…」で切り詰められ、表の列が潰れて読めなくなっていた問題を、MarkdownUI のどこに何を効かせて直したかの決定。
> **書かないもの**: 表テーマに `fixedSize` を付けると main thread が張り付く機序（→ [macOS ADR 0045](../../../macos/docs/adr/0045-remove-fixedsize-from-chat-table-styles.md)）、段落・見出しの `fixedSize` を macOS 側で先に導入した経緯（→ [macOS ADR 0118](../../../macos/docs/adr/0118-transcript-text-truncation-overlap.md)）。

## 文脈

モバイルのチャット本文で、次の3つが起きていた。

1. **段落・見出しが1行分の高さに潰れ、末尾が「…」で切り詰められる**。MarkdownUI の空テーマは段落・見出しの label に縦サイズ確保を付けないため、幅制約下で折り返しても親が1行高のままになる。
2. **表の列が容器幅へ圧縮され、セルの中身が読めない**。MarkdownUI は与えられた幅に列を詰め込む。iPhone の幅では列数が増えるほど1列が細くなり、文字が1文字ずつ折り返される。
3. **ターミナルセッションの出力が「出力」の行とトグルだけになり、中身が出ない**。出力本体が縦スクロールの提案する確定高へ丸められ、横方向もビューポート幅へクランプされていた。

ユーザーの要望は「とにかくアプリで確認できないような状態にすべきではない」。折り返して読ませるか、横スクロールで読ませるかのどちらかで、必ず全文へ到達できることを要求している。

制約として **macOS ADR 0045** がある。表のテーマ（`.table` / `.tableCell`）に `fixedSize` を付けると、幅の提案とレイアウトが収束せず main thread が 100% に張り付く。同じ罠を iOS で踏み直すわけにいかない。

## 決定

1. **段落・見出しのテーマにだけ縦サイズ確保を付ける**（`.paragraph` / `.heading1`〜`.heading6` に `fixedSize(horizontal: false, vertical: true)`）。macOS ADR 0118 と同方針。**表テーマには付けない**。
2. **GFM の表は段落から切り出し、別のブロックとして描く**。表判定は GFM の定義に寄せる（ダッシュ1個以上・単一列・エスケープされたパイプは区切りにしない・ヘッダ行と区切り行のセル数一致・4スペースインデントは対象外・リスト項目内のインデント表は切り出さない）。
3. **表に渡す幅は、表の本文から純関数で見積もる**。列ごとに全行の最長セルを取り、全角を2単位・半角を1単位として 1単位 8pt ＋ 列余白 32pt で合計する。結果は `max(容器幅, min(見積り, 2400pt))` にクランプし、その有限幅を `ScrollView(.horizontal)` の中の表へ渡す。
4. **ターミナル出力の本体は `fixedSize(horizontal: true, vertical: true)` で横クランプと縦の丸めを外し、横スクロールに載せる**。

## 棄却案

- **表テーマに `fixedSize` を付ける**: ADR 0045 の再発。幅の提案が収束せず main thread が張り付く。
- **表へ `fixedSize(horizontal: true)` で自然幅を取らせる**: 幅の提案が非有界になり、同じ非収束の一線を踏む。MarkdownUI へ渡す幅は常に有限でなければならない。
- **幅を固定値（960pt 等）にする**: 根拠のない魔法の定数になる。実測で、8列の表では 960pt でも列が圧縮されたままだった（自然幅は 1408pt 相当）。逆に小さい表では右側に無駄な空白域が残り、意味のない横スクロールが生じる。
- **セルを切り詰めて省略記号を出す**: 要望「アプリで確認できない状態にしない」に正面から反する。
- **表の判定を緩め、区切り行のセル数がヘッダ以下なら表とみなす**: GFM に反する。崩れた表入力を横スクロールへ閉じ込めてしまう。
- **インラインコード内の素のパイプをセル区切りとして数えない**: GFM は「inline span の内側でもパイプを含めるにはエスケープが必要」と定めており、cmark-gfm（MarkdownUI の実体）の HTML 出力を直接観測しても表にならない。実レンダラと判定をずらすと、表として切り出したものが表として描かれない。

## 結果

- 8列の表で、見積り 1408pt を渡したときの高さが自然幅の飽和値と一致した（960pt では 163pt、見積り幅では 109pt）＝列の圧縮が実際に解けている。
- 幅の見積りは容器幅について単調非減少かつ 2400pt で有界で、`NaN` / `inf` を渡しても有限値を返す。実ライフサイクル計測でレイアウトは 12〜14 回で収束し、ADR 0045 の非収束は再発していない。
- cmark-gfm との地上検証 17 ケースのうち 16 ケースで判定が一致した。唯一の相違はリスト項目内のインデント表で、これは「リストを分断しない」ことを優先した意図的な判断。
- 表テーマへの `fixedSize` 混入は、ソースに `.table {` / `.tableCell {` が現れないことをテストで凍結している。
