# ADR 0035: モバイルのターミナルは画面幅に収め、トグルに畳まない

> **このファイルの役割**: 端末画面を「横スクロールしない・折りたたまない」表示へ変えた決定と、幅の詰め方。
> **書かないもの**: SwiftTerm で描くこと自体の決定（→ [ADR 0034](0034-mobile-terminal-rendered-with-swiftterm.md)）、Mac が色つき画面を配信する仕組み（→ [macos/docs/adr/0126](../../../macos/docs/adr/0126-output-endpoint-serves-ansi-screen.md)）。

[ADR 0034](0034-mobile-terminal-rendered-with-swiftterm.md) の決定 2・3・7 を覆す。1・4・5・6 はそのまま生きている。

> **決定 3 は覆されている**: 「行数を見積もって高さを決める」は
> [ADR 0037](0037-mobile-terminal-is-styled-text-not-an-emulator.md) が置き換えた
> （見積もりが 1 行でも足りないと先頭が消えるため、高さは中身に決めさせる）。
>
> **決定 2 も覆されている**: 「収まらなければ折り返す（桁揃えより読めることを優先）」は
> [ADR 0038](0038-mobile-terminal-keeps-the-column-grid.md) が置き換えた。下の結果欄が予見していた
> 「罫線の折り返しぶんが半端な長さで残る」を、実機のユーザーが崩れとして拒否した。
> 収まらない分は折り返さず横スクロールで読む。決定 1・4・5 はそのまま生きている。

## 文脈

ADR 0034 は「Mac の桁数を守り、はみ出す分は横スクロールで読ませる」と決めた。実機で使ったユーザーの判断は逆だった。

> ターミナルの出力は出力トグルの中に出すんじゃなくて普通に画面に全て出して欲しい。
> モバイル用に幅とかは最適化しないといちいちサイドスクロールしないといけないから UX として良くない

前提が間違っていた。ADR 0034 は「Mac と同じ折り返し位置」を守るべき制約として扱ったが、実際に守るべきなのは**1行を1回のスクロールで読み切れること**だった。行ごとに横へ振らされる端末は、桁が揃っていても読めない。

「出力」の見出しとトグルも同じ理由で外す。端末画面は本文ではなく**今の画面そのもの**で、畳んだ状態に意味がない。12行を超えたら畳むという既存規則（ADR 0034 決定 7）は、端末には当てはまらない。

## 決定

**幅は常に与えられた画面幅に収める。横スクロールは作らない。**

1. **まずフォントを縮めて Mac の桁数を収めにいく**。折り返し位置が Mac と一致していれば TUI の枠線・表が崩れないので、収まるなら桁を守るのが最善。
2. **読める下限（7pt）まで縮めても収まらなければ折り返す**。桁揃えより読めることを優先する。iPhone の本文幅では 85 桁前後が下限で、それより広い Mac 端末（120 桁など）は折り返す。枠線は崩れるが、全文が縦スクロールだけで読める。
3. **行数は折り返した後の数で見積もる**。全角は 2 桁として数え、さらに 1 行ぶん多く確保する。少なく見積もると端末が先頭行をスクロールで捨てる（＝上が読めなくなる）が、多い分は末尾の空行で済む。
4. **端末画面は見出しにもトグルにも入れず、そのまま全文を出す**。色つきで来なかったときの等幅テキスト経路は従来どおり「出力」カード＋トグル＋横スクロールのまま（本文の桁を守る意味がまだあるため）。
5. **端末だけは本文の左右余白を打ち消して画面端まで使う**。1桁でも多く見せたいので、他のカードと余白を揃えるより桁数を優先する。
5. **幅は高さ 0 のプローブで測る**。端末自身に測らせると、幅が決まる前に桁数が決まって折り返しがずれる。

## 棄却案

- **Mac の桁数を守って横スクロール（＝ ADR 0034 の元の決定）**: ユーザーが実機で否定した。
- **画面幅に合わせて Mac 側の端末を縮める**: 折り返しを両側で一致させられるが、デスクトップの表示まで巻き添えで狭くなる。モバイルの都合で Mac の作業画面を壊さない。
- **常に折り返す（フォントを縮めない）**: 実装は単純だが、80 桁程度の TUI なら縮めるだけで枠線を保てるのに、それを捨てることになる。
- **ピンチで拡大縮小させる**: 読み取り専用ビューに操作を足すと、親のスクロールとジェスチャが競合する。既定で読める状態にするほうが先。

## 結果

- シミュレータで確認した: 80 桁のモックは折り返さずに収まり、120 桁・全角・256色・背景色・下線・dim を混ぜたモックは折り返して全文が縦スクロールだけで読めた。色はいずれも出た。
- **実機の Mac 端末は 138 桁だった**（2026-07-27 実測）。iPhone の本文幅では下限 7pt でも 90〜100 桁までしか入らないので、この幅は**折り返す**。偽サーバーへ 138 桁の Claude Code 風スクリーンを流して iOS 26.2 シミュレータで確認したところ、色（256色・dim・シアン/マゼンタ/黄/緑）は正しく出て、長い行と罫線は2行に折り返り、横スクロールなしで全文が読めた。罫線の折り返しぶんが半端な長さで残るのは、この幅を諦めない限り避けられない。
- `TerminalScreenMetricsTests` を 13 件へ書き換え、PhloxKit 575 件が green。
- **未検証**: 実機での見え方（実際のエージェント TUI をこの幅詰めで読んだときの可読性）。ユーザー確認待ち。
- 下限 7pt は「読める最小」の主観的な線引きで、根拠は実測ではない。実機で小さすぎると分かれば折り返し寄りへ動かす。
