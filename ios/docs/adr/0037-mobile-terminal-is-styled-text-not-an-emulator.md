# ADR 0037: モバイルの端末画面は装飾付きテキストとして描く（端末エミュレータを使わない）

> **このファイルの役割**: 端末エミュレータ（SwiftTerm）による描画をやめ、SGR を解釈した装飾付きテキストへ替えた決定と、その理由。
> **書かないもの**: 幅の詰め方（→ [ADR 0035](0035-mobile-terminal-fits-screen-width.md)。決定 1・2・4・5 はそのまま生きている）、Mac が色つき画面を配信する仕組み（→ [macos/docs/adr/0126](../../../macos/docs/adr/0126-output-endpoint-serves-ansi-screen.md)）、履歴（スクロールバック）を配信範囲へ含める決定（→ [macos/docs/adr/0127](../../../macos/docs/adr/0127-ansi-output-includes-scrollback.md)）。

[ADR 0034](0034-mobile-terminal-rendered-with-swiftterm.md) を全面的に置き換える。[ADR 0035](0035-mobile-terminal-fits-screen-width.md) の決定 3（行数を見積もって高さを決める）も置き換える。

## 文脈

実機で開いた端末が**上半分しか表示されず、しかもスクロールできなかった**（ユーザー報告: 「ターミナルが上半分しか表示されていない上にスクロールもできない」）。画面の先頭（起動バナー・最初のやり取り）が丸ごと欠け、途中の行から始まっていた。

**原因は 2 つあり、独立している。**「上半分しか出ない」は本 ADR が扱う描画方式（下記）、「スクロールできない」は**そもそも履歴が届いていなかった**こと（→ [macos/docs/adr/0127](../../../macos/docs/adr/0127-ansi-output-includes-scrollback.md)）である。前者だけを直した時点で再確認したところ、届いた分は 1 行残らず描かれているのにユーザーからは「スクロールできません」が続いた——受け手を直しても、画面に収まる分しか送られていなければ遡れない。

### 「上半分しか出ない」の原因（本 ADR の対象）

描画方式そのものにある。

- 端末エミュレータ（`SwiftTerm.TerminalView`）は**固定行数の格子とスクロールバック**を持つ。格子は frame の高さから決まるので、こちらが渡した高さが中身より低いと、**あふれた先頭行はスクロールバックへ流れて画面から消える**。
- その高さは、[ADR 0034](0034-mobile-terminal-rendered-with-swiftterm.md) 決定 4 と [ADR 0035](0035-mobile-terminal-fits-screen-width.md) 決定 3 に従って**こちらが見積もっていた**。SwiftTerm の内部セル寸法は非公開なので、同じフォントで同じ式（`"W"` の advance、ascent+descent+leading の切り上げ）を再現し、全角を 2 桁と数え、さらに 1 行ぶん多く積む——という**再実装**である。
- 再実装が SwiftTerm の実際の桁数を 1 桁でも上回れば、SwiftTerm 側の折り返しはこちらの見積もりより増え、増えた分だけ先頭が消える。しかも読み取り専用（`isUserInteractionEnabled = false`）なのでスクロールバックへ戻す手段が無い。**消えたことに気づく手段も無い。**
- ADR 0035 決定 3 はこの失敗を予見して「1 行ぶん多く確保する」と書いていた。安全余裕は足りなかった。全角判定の近似・絵文字・罫線・SwiftTerm 側の丸めなど、ずれる要因は 1 行では収まらない。

ここで初めて前提を疑った。**この画面にエミュレータは要らない。** Mac が配信するのは `AnsiScreenEncoder` が書き出した「SGR ＋ 本文 ＋ 改行」だけで、カーソル移動も画面消去もスクロールも含まない。エミュレータが持つ機能のうち、ここで使っているのは SGR の解釈だけである。にもかかわらず、格子・スクロールバック・寸法の再実装という、**この用途では害しかない仕組み**を丸ごと抱え込んでいた。

## 決定

**受け取った画面を行ごと・SGR ごとの塊へ分解し、`AttributedString` の `Text` を 1 行につき 1 つ並べて描く。端末エミュレータには依存しない。**

1. **`AnsiTextParser` が SGR を解釈する**。対応するのは Mac が実際に出す範囲——リセット・太字・淡色・斜体・下線・反転・取り消し線、30〜37 / 90〜97 / 40〜47 / 100〜107、`38;5;n` / `48;5;n`（xterm 256）、`38;2;r;g;b` / `48;2;r;g;b`（true color）、39 / 49。SGR 以外の CSI（`ESC[?25l` 等）は読み飛ばし、本文へ漏らさない。
2. **高さは中身が決める**。`fixedSize(horizontal: false, vertical: true)` で `Text` が要求する高さをそのまま使う。**こちらは高さを一切見積もらない**ので、見積もりのずれで中身が消える経路が原理的に無くなる。画面より高い分は親の `ScrollView` で読む。
3. **SwiftTerm 依存を iOS から外す**。`PhloxKit` の依存から vendored fork を削り、セル寸法の再実装（`TerminalScreenLayout` / `wrappedRowCount` / `displayWidth`）も消す。Mac 側 `TerminalUI` は引き続き SwiftTerm を使う（あちらは本物の端末なので当然要る）。
4. **フォントサイズの決定は ADR 0035 のまま**。Mac の桁数が収まるところまで縮め、下限 7pt で止める。収まらない行は SwiftUI のテキスト折り返しに任せる（エミュレータの格子ではなくなったので、折り返しは通常のテキスト折り返しになる）。
   - **［2026-07-27 折り返しの部分のみ superseded → [ADR 0038](0038-mobile-terminal-keeps-the-column-grid.md)］** 折り返すと表・罫線が崩れると実機で分かった。収まらない分は折り返さず横スクロールで読む。フォントを縮めて収めにいく手順は変わらない。
5. **端末を出している画面は、本文の地も端末の色で塗る**。中身が短い日は端末の下に余白が残る。地の色が違うと「上半分しか出ていない」ように見え、今回の不具合と区別がつかない。
6. **パーサはプラットフォーム非依存にしてホストで検証する**。`#if os(iOS)` の中に置くと `swift test`（macOS ホスト）でコンパイルすらされず、この層のバグをテストで捉えられない（→ レッスン L-45）。
7. **1 行 = 1 つの `Text` を `LazyVStack` に並べる**。ADR 0127 で履歴ごと届くようになり、行数は数百〜数千になる。全部を 1 つの `AttributedString` に組むと、画面外の行まで含めて毎回テキストレイアウトが走る。行で切って遅延描画すれば、実際に見えている行だけが組まれる。空行は 1 行ぶんの高さを保つため空白 1 文字として描く（空文字は高さ 0 になり行間が詰まる）。SGR は行をまたいで持ち越す（端末の SGR は改行では戻らない）。
8. **解析は画面が変わったときだけ行う**。`body` のたびに数千行を舐め直すと描画が詰まるので、`onChange(of: screen.text, initial: true)` で結果を保持する。

## 結果

- 実機実測と同じ 138 桁 × 49 行の画面を偽サーバーから配信し、シミュレータ（iPhone 17 / iOS 26.2）で先頭行から最終行まで欠けずに描かれることを確認した。
- 回帰は 2 層で守る。①`AnsiTextParserTests`（ホスト）が「装飾を剥がした本文が 1 文字も欠けない」ことを縛る。②`TerminalScreenWiringTests` が「固定高さへ嵌め直さない」「エミュレータを埋め込まない」という配線を凍結する（値型のテストだけでは View の配線を戻されても気づけない → レッスン L-67）。③`SessionTerminalLiveRegressionUITests`（ライブ・既定スイート外）が実画面で先頭行と最終行の同居を確認する。
- 138 桁は 7pt でも iPhone の幅に収まらないため、全幅の罫線は 2 行に折り返す。ADR 0035 決定 2 の「桁揃えより読めることを優先する」に従った結果で、本 ADR では変えない。

## 棄却案

- **エミュレータのまま、描画後に実際の行数を聞いて高さを直す**: SwiftTerm に「今の中身が何行か」を聞いて SwiftUI へ返す測定ループが要る。レイアウトの往復が増えるうえ、格子とスクロールバックという「あふれたら捨てる」性質は残るので、ずれた瞬間にまた消える。原因を残したまま検出を足すだけになる。
- **エミュレータのまま、高さを十分大きく取る（安全余裕を増やす）**: 今回と同じ設計のまま定数を大きくするだけで、いつまた足りなくなるか分からない。余裕が過剰なときは末尾に巨大な空白が出る。
- **Mac 側で装飾付きの構造化データ（run の配列）を送る**: 受け手のパースは不要になるが、ワイヤ契約の変更と Mac 側の実装が要る割に、SGR のパースは小さく完全にテストできる。契約は据え置く。
- **`UITextView` に `NSAttributedString` を渡す**: 高さの計算を自前でやることになり（`UIViewRepresentable` は intrinsic size を自動で伝えない）、今回の失敗と同じ構図へ戻る。
- **行で切らず、画面全体を 1 つの `Text` のまま描く**: テキスト選択が行をまたげる利点があるが、数百〜数千行ぶんの `AttributedString` を毎回組んでレイアウトすることになる。選択が 1 行単位になる不便より、開くたびに固まる方が重い。
