# Claude Design 用プロンプト集 — ファイルツリー・Markdown/HTML 表示・iOS シミュレーター

既存 UI の全面再設計用の `claude-design-prompts.md` とは別物。こちらは**今の Phlox の見た目に、新機能を足す**ためのプロンプト。

## 使い方

1. Claude Design で新しいプロジェクトを作り、次の 2 つの設計書を添付する（要件の正本）。
   - `macos/docs/specs/file-explorer-and-markdown-editing.md`
   - `macos/docs/specs/embedded-ios-simulator.md`
   - あれば今の Phlox のスクリーンショット（メインウィンドウの single 表示・右サイドバーを開いた状態・ファイルタブ）も添付する。
2. 最初に「0. 共通プロンプト」を送る。
3. 「1. 配置の確認」で全体の置き場所を確定させてから、2 以降を 1 つずつ送る。
4. 最後に「8. 横断レビュー」で、設計書の要件の抜け漏れと見た目の一貫性を点検させる。

各プロンプトの「参照」は設計書の章番号（FR = 機能要件、§ = 章）。

## 0. 共通プロンプト（最初に 1 回だけ送る）

```
あなたは macOS ネイティブアプリの UI デザイナーです。Phlox という macOS デスクトップアプリに、新しい機能の画面を足します。
添付の 2 つの設計書が要件の正本です。今の Phlox の見た目と操作感に溶け込む、高忠実度のモックを作ってください。
既存の画面を作り直すのではなく、既存の画面に新しい要素を足す、という前提です。

## Phlox とは
複数の AI コーディングエージェント（Claude Code / Codex / Cursor）を 1 つのウィンドウで同時に走らせ、
監視・指示・承認する開発者向けアプリ。利用者は数〜十数のセッションを並行させる上級開発者。

## 今のメインウィンドウの構成（ここに足す）
- 上部ツールバー（高さ 52pt）。
- 左サイドバー（幅 220〜360pt）: プロジェクトとセッションの一覧。
- 中央: 上段にセッションのタブ列（高さ 32pt）、その下に子タブ列（高さ 32pt。会話・ターミナル・変更・ファイル）。
  子タブは左右 2 区画に分割できる（⌘\）。分割の各区画は最小 320pt。
- 右サイドバー（インスペクタ。幅 260〜340pt）: 上部の切り替え「セッション / 使用量」。中央が 480pt を割ると重ね表示（浮いたカード）になる。
- ファイルの子タブ: 高さ 30pt の帯（ファイルパス・「未保存」・「保存 ⌘S」ボタン）＋行番号付きの等幅エディタ。

## 今のデザインの値（既定のダークテーマ「Phlox」。コード上の正本は Packages/DesignSystem）
- 基調はモノクロのグレー階調、アクセントはコーラル 1 色だけ。
- 背景: ウィンドウ #1E1E20 / サイドバー #262629 / ツールバー #2A2A2D / パネル #242427 / カード #27272A /
  コード #2B2B2F / 入力欄 #1A1A1C / ポップオーバー #2F2F33 / タブ列 #232326 / ターミナル #141416
- 文字: 主 #F2F2F4 / 副 #ABABB1 / 補助 #8E8E94。区切り線は主文字色の 10%、枠線は 14%。
- アクセント: #E08865（コーラル）。選択の塗りは主文字色の半透明。
- 注意の色（印 / 文字）: 承認待ち #F0AE4A / #F4BD68、質問 #5D98F0 / #8DB6F7、エラー #EE5A5F / #FF8A8D、無応答 #A876EB / #C4A2F4。
- 差分: 追加 #6FD08C、削除 #FF8A8D。
- 文字サイズ: 行 13pt、補助 12pt、メタ情報 11pt、等幅 11pt、セッション名 14pt semibold。システムフォント（SF Pro / SF Mono）。
- 間隔は 8pt グリッド（2 / 4 / 8 / 12 / 16 / 24 / 32）。角丸: タグ 4、ボタン・行 6、カード 8、パネル 10、入力欄・シート 12。
- 一覧の行の高さ 28pt。アイコンは SF Symbols。
- ライトテーマもある。主要な画面はダークで作り、最後にライトでも成り立つかを 1 枚確認する。

## デザイン原則
- macOS Human Interface Guidelines に沿う。静かな chrome（装飾を足さない）。注意が必要なものだけが目立つ。
- 状態は色だけに頼らず、アイコン・文言でも区別できること。
- キーボードだけで全操作できること。VoiceOver のラベルと操作を意識する。
- UI 文言は日本語（英語に切り替えても崩れない幅を確保する）。

## 各画面の出力ルール
- (1) 通常状態 (2) 設計書にある状態の描き分け（空・読み込み中・エラー・非対応など）(3) 主要な操作の途中（ホバー・クリック後・右クリックメニュー・確認ダイアログ）。
- モックの横に「要件対応表」を付ける: 設計書の FR 番号 → モック上の置き場所。置けなかった要件は明記する。
- 設計書の「スコープ外」にある機能（ファイルの作成・削除、書式ツールバー、HTML のスクリプト実行、端末の回転など）は描かない。
- サンプルデータは現実的に: 実在しそうなリポジトリ（例: `phlox-oss`、ブランチ `feature/file-tree`）、ファイル名、Markdown 文書、iPhone の画面。

まずは了解の返事と、設計書を読んで気づいた「UI 上の難所」を 5 つ以内で挙げてください。モックはまだ作らないでください。
```

## 1. 配置の確認（全体の置き場所）

```
新機能の置き場所を、メインウィンドウ全体のモックで示してください。参照: ファイル側 §0・§3.3、シミュレーター側 §0・§3.4。

描くもの:
- 右サイドバーの切り替えが「セッション / ファイル / 使用量」の 3 つになった状態で、「ファイル」を選んでいる。
- 中央は子タブを左右に分割: 左に Markdown のファイルタブ、右に「シミュレーター」の子タブ（iPhone の画面）。
- 子タブ列の「＋」メニューに「シミュレーター」が増えている状態（ポップオーバー展開時）。

描き分け:
- ウィンドウ幅 1600pt（全部並ぶ）/ 1200pt（右サイドバーが重ね表示になる）/ 左サイドバーを隠した状態。

論点として提案してほしいこと:
- 右サイドバーの幅（最大 340pt）でツリーと iPhone 画面が窮屈にならないか。窮屈なら代案を、既存の構成を壊さない範囲で。
```

## 2. 右サイドバーのファイルツリー

```
右サイドバーの「ファイル」タブを設計してください。参照: ファイル側 FR-1〜FR-7、§3.3。

含めるもの:
- 上部: ルートのパスとブランチ名（例: `~/Projects/phlox-oss`・`feature/file-tree`）、更新ボタン。
  ブランチ表示の描き分け: 通常 / detached HEAD（コミット短縮名）/ Git 管理外 / 取得失敗（空欄）。
- ツリー本体: 開閉三角・フォルダ/ファイルのアイコン・名前・深さぶんの字下げ（行 28pt）。フォルダ先・名前の自然順。
- 選択状態（中央で開いているファイルに対応する行）、ホバー、キーボードフォーカス。
- symlink の 3 種: ルート内のファイル（開ける）/ フォルダへの symlink（展開しない）/ ルート外を指すもの（薄く表示、開けない理由）。
- 1 フォルダ 5,000 件を超えたときの末尾表示「ほか N 件（⌘P で開けます）」。
- 右クリックメニュー: 「右に分割して開く」「Finder で表示」「パスをコピー」。

描き分け:
- セッション未選択の空状態 / ルートが読めない（理由＋更新ボタン）/ フォルダ読み込み中 / フォルダの読み込みエラー。
- 重ね表示（浮いたカード）になったとき。
```

## 3. ファイルタブの帯と、開けないファイルの表示

```
ファイルの子タブの上部の帯と、開けないファイルの表示を設計してください。参照: ファイル側 FR-8・FR-10・FR-13、§3.2 (a)(c)、§3.4「モード切替」。

含めるもの:
- 高さ 30pt の帯: ファイルパス（先頭を省略）・「レンダリング / ソース」の切り替え（⌃⌘M）・「未保存」・「保存 ⌘S」。
  切り替えは .md / .markdown / .html / .htm のときだけ出る。それ以外のファイルでは出ない。
- 帯に出す理由表示: 「このファイルは大きすぎるためソース表示に固定しています」など（Markdown が 2,000 ブロック超・500 KB 超）。

開けないファイルの表示（中央の空状態として。どれにも理由と次の行動を出す）:
- 大きすぎる（1 MB 超）→「既定のアプリで開く」
- バイナリ → 「既定のアプリで開く」
- 作業ツリーの外を指している → 解決先のパスを表示＋「Finder で表示」
- UTF-8 として読めない（既存の「ファイルを開けません」）
```

## 4. Markdown のブロック編集

```
Markdown ファイルを、レンダリングした状態のままブロック単位で編集する画面を設計してください。参照: ファイル側 FR-8〜FR-12、§3.4。

前提: 見出し・段落・リスト・表・コードなどの「ブロック」をレンダリング表示し、クリックしたブロックだけがその場で原文
（Markdown 記法そのもの）の入力欄に変わる。Notion のような書式ツールバーは無い。編集は原文を直接書く。

含めるもの（サンプル文書は README 風に: front matter・見出し・段落・箇条書き・表・コードブロック・参照リンクを含める）:
- 通常: レンダリング表示。ホバーしたブロックに薄い背景。
- 編集中: 1 ブロックだけ原文の入力欄（等幅・行番号なし・最大高さ付きで中をスクロール）。前後のブロックはレンダリングのまま。
  確定の方法（Esc・ブロック外クリック・⌘Return）が分かる控えめな手がかり。
- front matter: 文書先頭の等幅のブロック（原文編集のみ）。
- 「原文」ブロック: 中身が参照定義だけの文書など、描画できる要素が無い区間を薄い原文で表示したもの。
- 未確定の編集がある状態での「未保存」表示。
- 編集できない状態の帯表示（「外部で内容が変わったため確定できません」）。

描き分け:
- 空の文書（1 つだけ空のブロックを出し、クリックで書き始められる）。
- キーボード操作中（↑↓ でブロック選択、Return で編集開始）のフォーカス表示。
- リンクの上にホバーしたとき（リンクのクリックは編集開始より優先）。

論点として提案してほしいこと:
- 編集中のブロックと表示中のブロックの境目が分かり、かつうるさくない見せ方。
- 「ブロックをまたぐ選択はできない（ソース表示で行う）」という制限を、どう自然に伝えるか。
```

## 5. HTML の表示

```
HTML ファイルの閲覧専用レンダリング表示を設計してください。参照: ファイル側 FR-13〜FR-15、§3.5。

前提: 表示は閲覧専用。編集は「ソース」に切り替えて行う。スクリプトは常に止め、ページからの外部通信も常に遮断する
（外部の画像・CSS・フォントは読み込まれない）。これは安全のための仕様で、切り替えるトグルは無い。

含めるもの:
- 帯: 「レンダリング / ソース」・再読込ボタン・「未保存」・「保存 ⌘S」。
- 外部リソースが遮断されたことの控えめな表示（例: 「外部の 3 件を読み込んでいません」）。うるさくしない。
- ページ内リンクのホバー（作業ツリー内の .html / .md はファイルタブで開く、http(s) はブラウザで開く、の区別が分かる）。

描き分け:
- 未保存の編集を反映した表示（ソースで編集 → レンダリングに戻った直後）。
- 表示が停止した（「表示が停止しました。再読込」）。
- 遮断の準備に失敗してプレビューを出さない（ソース表示＋理由）。
```

## 7. iOS シミュレーターの子タブ

```
iOS シミュレーターの画面を表示・操作する子タブを設計してください。参照: シミュレーター側 FR-1〜FR-9、NFR-2・NFR-4、§3.3・§3.4。

含めるもの:
- 帯: 端末の選択（「iPhone 17 · iOS 26.2」。起動中の端末を先頭、状態の印つき）・ホーム・スクリーンショット・停止・状態表示。
- 画面: iPhone の画面を縦横比を保って中央に表示（周りは余白）。端末の外枠（ベゼル）は描くか描かないかを提案する。
- タブにフォーカスがあり、キー入力が端末に送られている状態の表示（Mac 側の操作と区別できること）。
- 停止の確認ダイアログ: 「この端末を表示中の他のタブ・Phlox の別の版・Simulator.app にも影響します」。

描き分け（どれにも理由と次の行動）:
- 端末が停止中（「起動」ボタン）/ 起動中（進行表示）。
- 未確認の組み合わせ（Xcode と iOS のバージョン）:「未確認でも試す」「Simulator.app で開く」。
- 表示はできるが入力は未確認: 表示だけ有効、帯にその旨。
- Xcode が見つからない / 補助プロセスに接続できない（「再接続」）/ アプリの再起動が必要（版の不一致）。
- 診断「画面更新を観測していません」（エラーではなく控えめな情報として）。
- 右区画の幅 320pt（狭い）と 700pt（広い）。

論点として提案してほしいこと:
- 「画面の中の操作は iPhone に届く」「⌘ 付きのキーは Phlox のショートカット」という境界を、利用者が迷わない見せ方。
- 端末内の UI は VoiceOver で操作できない（画面は画像のため）。帯は操作できる。この制限の伝え方。
```

## 9. 修正依頼（2 回目のレビュー結果。2026-10-02）

```
2 回目のレビュー結果です。次の修正をしてください。設計書（添付の 2 つ）が正本です。修正後は、各項目をどう直したかを一覧で返してください。
1・2 は前回の修正が反映されていません（ファイルが前回と同一でした）。必ず直してください。

## 1 配置
- 論点2 の推奨「C. インスペクタを 260pt まで自動で縮める」と、論点3 の推奨「A. ファイルを開いたらカードを閉じる」を取り下げる。
  どちらも設計書（幅の規則 PaneWidthPolicy は変えない・FR-3 に無い挙動）に反する。推奨は置かず、「未決の論点」として事実だけ書く:
  「1200pt で左右に分割すると各区画が 320pt を下回る」。
- 1b の見出しとキャプションを、実際に重ね表示になる幅（中央が 480pt を下回る幅。例: 1000pt）に直す。1200pt の見本は「並んで表示・分割区画が 320pt を割る」状態として別に描く。
- 設計書に無い要素を消す: 論点4 の「区画を端末の幅に合わせる」メニュー、区画の「左」「右」ラベル。
- 論点1 の長いパス（macos/Packages/…/FileTreeView.swift）がカードの右端からはみ出している。先頭を省略して収める。
- 「端末」と「ターミナル」の表記を分ける: iOS シミュレーターは「端末」、シェルは「ターミナル」。

## 2 ファイルツリー
- 2h のフォルダごとの「再試行」ボタンを消す（設計書では、上部の更新ボタンかフォルダの再展開で読み直す）。エラー文だけ残す。
- 更新ボタンの名前を「更新」に統一する（「再読込」は使わない。HTML の再読込とは別物）。
- 2d のツールチップの `/Users/kaito/...` を `~/...` 表記にする。

## 3 ファイルタブの帯
- 3i・3j・3k でパスが省略されていない。長いパス（例: macos/docs/guides/vision-testing-desktop-ui.md）にして、先頭側の省略（…/guides/…）を実演する。
- 3j・3k の本文の 2 つ目の箇条書きが枠の下端で半分切れている。枠を伸ばすか内容を減らす。

## 4 Markdown のブロック編集
- 確定方法の手がかりを「⌘Return・Esc・ブロックの外をクリックで確定」にする。
- 4g の理由文を「文書が先に変わったため確定できません」にする（外部でのファイル変更とは別物。外部変更は保存時の競合ダイアログが扱う）。
- 帯のファイルパスを 3 と同じく先頭側で省略する。
- 4d: キャプションの「最大 12 行」を、実際の最大高さに合う行数にする。最大高さの実演なら、内容を最大高さより長くしてスクロールさせる（今は内容が収まっているのにスクロールバーがある）。原文の表を 4a の描画結果と同じ内容にする。
- 4i・4m のツールチップが次の見出しに重なっている。位置をずらす。
- 4h の「Return で編集」バッジが表の枠線に被っている。
- アクセシビリティ:
  - 表示切り替えの aria-label は「表示」だけにし、⌃⌘M は aria-description に分ける。保存ボタンも同様（label「保存」、description「⌘S」）。
  - 見出しブロックで group の aria-label と見出しが二重に読まれないようにする。
  - リンクの中に tooltip を入れ子にしない。

## 5 HTML の表示
- 「外部の 3 件」のような件数表示をやめ、固定の文言「外部の読み込みを止めています」にする。件数や遮断した URL の一覧は出さない（WebKit の遮断の仕組みは件数も URL も返さないため）。
  5b のポップオーバーも一覧をやめ、説明文だけにする。
- 「リンクの扱い」表の「フォームの送信。左下に『開きません』と出し」を「フォームの送信は何も起きない」に直す（フォームにはホバーが無い）。
```
