# ADR 0126: セッション保存は未知の値を要素単位で捨て、原本を残す

> **このファイルの役割**: `sessions.json` に未知の列挙値が1件でも入ると全セッションが消えていた問題を、なぜ「要素単位の除外＋原本コピー」で直したかの決定。
> **書かないもの**: `SessionLaunchContext` に区分を足した理由（→ [ADR 0127](0127-control-api-requester-parent-separation.md)）、JSON ストア共通の隔離方針そのもの（`MessageStore/JSONFileStore.swift` の実装）。

## 文脈

`SessionLaunchContext` は `String, Codable` の列挙で、`decodeIfPresent(...) ?? .interactive` で読んでいた。この `?? .interactive` は **キーが無いとき**しか効かない。**キーはあるが値が未知**（新しい区分を足した新版で保存し、旧版で読む／逆方向のダウングレード）なら `decode` が throw する。

さらに `JSONFileStore.load()` は**ファイル全体を1回で decode** する実装のため、1件の未知値で配列全体の decode が失敗し、ファイルが隔離されて**全セッションが失われる**。

この run では新しい区分（`.remoteUser`）を足す必要があった（→ ADR 0127）。前方互換が無いままそれをやると、その版で作ったデータを旧版で開いた瞬間に全滅する。**区分追加の前提条件**として先に直す必要があった。

## 決定

1. **要素単位で decode する**。1件の descriptor が壊れていても、他の descriptor は読み込む。壊れた1件だけを捨てる。
2. **捨てた事実を追跡可能にする**。警告ログに **session id**（取得できなければ `unavailable`）と decode エラーを出す。
3. **原本を残す**。捨てた要素があったときは、元のファイルを `.corrupt-<epoch>` としてコピーする（**移動ではなくコピー**。原本は正常な内容で上書き保存される）。同一内容のバックアップは重複作成しない。

## 棄却案

- **`?? .interactive` のままにして、未知値だけ握りつぶす**: 未知値を既定値へ丸めると、旧版で開いた瞬間に区分情報が失われ、保存し直した時点で**新版へ戻しても復元できない**。静かなデータ破壊になる。
- **`JSONFileStore` を要素単位 decode へ変える**: 共有面であり、セッション以外の利用者（メッセージ等）の隔離挙動まで変わる。影響範囲が広すぎる。セッション側の decode で閉じるほうが小さい。
- **捨てた要素を黙って落とす**: 独立レビューで「復元不能な恒久的データ喪失をログにも残さないのはエラー握りつぶしと同じ」と指摘され、追跡可能性（session id ＋原本コピー）を足した。

## 結果

- 未知値を含むファイルを読んでも、他のセッションは生き残る。壊れた1件は原本から手で復旧できる。
- 受け入れテスト `AcceptanceSessionStoreForwardCompatTests`（3件）で「他セッションを壊さない」「ファイルを隔離しない」「既知値・欠損は不変」を凍結。
- **既知の限界**: 前方互換が効くのは `launchContext` の未知値に対してであり、`backend` / `kind` など**他フィールドの未知値は依然として要素ごと落ちる**（＝そのセッション1件は失われる。ファイル全体は無事）。
- **既知の限界**: `.corrupt-` という名前が「隔離されたゴミ」と「復旧用バックアップ」の二義になっている。今回は後者の意味で使っている。
