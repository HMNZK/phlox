# ADR 0128: 通知は「その通知が届く先から辿れるセッション」にだけ出す

> **このファイルの役割**: 「通知しているのにユーザーがそれを解消できない」状態を構造的に不可能にした決定と、到達可能性を**届け先（Mac / iPhone）ごと**に判定することにした理由。
> **書かないもの**: セッションが画面に出るかどうかのルールそのもの（→ [ADR 0027](0027-grid-workspace-filter-includes-subsessions.md)）、赤表示（要対応）の導出（→ [ADR 0111](0111-awaiting-user-question-status.md)）、そもそも孤児が生まれる原因（→ [ADR 0127](0127-control-api-requester-parent-separation.md)）。

## 文脈

ユーザーへ働きかける出口は4つある: **Dock バッジ件数・通知バナー・完了音・APNs（プッシュ通知）**。調査時点では**どれも「そのセッションが画面に出るか」を見ていなかった**。

一方、要対応ラッチの解除（`markCompletionSeen`）は macOS の**「選択中セッション」でしか発火しない**。つまり画面に出ないセッションには解消手段が存在しない。

この非対称が、Dock バッジが永久に減らない症状の直接原因だった（バッジが数えていたのは、ユーザーがどうやっても既読にできないセッション）。

## 決定

**不変条件を1つ置く**:

> **あるクライアントへ通知する対象 ⊆ そのクライアントから到達して解消できる対象**

そのうえで、

1. **到達可能性の正本を1つにする**（`SessionReachability`）。判定は**届け先ごと**に行う。
2. **判定は各サーフェスの表示ルールの論理和として上に載せる**。サーフェス側のルール（ADR 0027）は一切変えない。
3. 出口と届け先の対応:

   | 出口 | 届け先 | 判定 |
   |---|---|---|
   | Dock バッジ件数 | macOS | `.desktop`（グリッド／ワークスペース絞り込み／サイドバーの論理和） |
   | 通知バナー | macOS | `.desktop` |
   | 完了音 | macOS | `.desktop` |
   | APNs | iPhone | `.mobile`（＝現状は全セッション） |

4. **層の依存方向を保つ**。判定は `DashboardFeature` が所有し、通知を出す `SessionFeature` へは「出してよいか」を返すクロージャとして**注入**する。注入されていなければ通知する（既定＝従来挙動）。
5. **判定は fail-open**。まだ一覧に登録されていないセッション（起動処理の途中）は「到達可能」とみなす。ここを閉じると、登録前に完了した通知が黙って落ちる。
6. **抑止するのは通知だけ**。要対応ラッチと赤表示の導出（ADR 0111）は変えない。

## なぜ届け先ごとに分けるか（当初は分けていなかった）

最初の設計は「4出口すべてを同一の判定で塞ぐ」だった。独立レビューで**誤りだと判明した**。

- APNs の受け手は iPhone であり、iPhone のセッション一覧（Control API の `controlSessionSummaries`）は **`launchContext` で絞り込まず全セッションを返す**。
- したがって「macOS の画面から辿れない」を理由に APNs を塞ぐと、**iPhone からは開けるのに通知が来ない**状態になる。これは「通知が黙って落ちる」方向の回帰で、症状が出ないぶん元の不具合より質が悪い。
- 逆に Dock バッジは macOS でしか既読にできないので、**macOS の到達可能性で判定しなければならない**。

つまり「どこから解消できるか」は出口ごとに違う。1つの述語で覆おうとしたのが誤りだった。

なお `.mobile` は現状 **常に true** を返す。これは「ゲートを付け忘れた」のではなく、**モバイル一覧の可視性ルールをここへ写した明示のポリシー**である。将来モバイル一覧に絞り込みを入れるときは、ここを直せば APNs の判定が同じルールへ自動追従する。コード上にも参照先つきで書いてある。

## 棄却案

- **モバイル一覧を macOS と同じ可視性ルールに揃える**: 1つの述語で全クライアントを覆えて最も単純。だが iPhone の一覧から実際にセッションが消える**ユーザー可視の挙動変更**であり、この不具合の修正に必要な範囲を超える。ADR 0027 は macOS のサーフェスについてのみ決めており、モバイル一覧を「全件」にした判断を覆す根拠がなかった。
- **APNs にはゲートを付けない（不作為）**: 今は同じ結果になるが、将来モバイル一覧に絞り込みが入ったとき静かに壊れる。ポリシーとして書き残すほうを採った。
- **バッジの集計だけ直す**: 症状は消えるが、バナー・音・APNs の非対称は残る。同種の不整合がまた生まれる。

## 結果

- 4出口すべてが単一の正本を参照する。同じ意味の集計が複数実装に分岐している状態も解消した（サイドバーの森走査を共通ヘルパーへ一本化）。
- 受け入れテスト `AcceptanceNotificationReachabilityTests` で、真理値表・実サーフェスとの一致・バッジの除外／非除外・チャネル別ゲート・PTY 完了と Chat 承認待ちの実経路・未注入時の既定を凍結。
- **検証範囲の限界**: バナーと完了音は `SessionCompletionNotifier` がテストバンドルで早期 return するため**テストから観測できない**。そのため「同じチャネルの出口を1つのメソッドへ集約し、その先頭にゲートを1つだけ置く」ことを実装契約とし、構造をレビューで確認している。
- **既知の近似**: iOS 側の一覧は未知の CLI 種別を落とすため、「モバイル＝全件到達可能」は厳密には近似（過剰に通知する側へ倒れるので、通知欠落は起きない）。
