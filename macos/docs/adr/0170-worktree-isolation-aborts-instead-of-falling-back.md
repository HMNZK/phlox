# ADR 0170: worktree 隔離に失敗したら起動を中止する（従来挙動へフォールバックしない）

> **このファイルの役割**: セッションごとの git worktree 隔離が失敗したときに「中止」を選んだ
> 決定と、その理由。
> **書かないもの**: 隔離機能そのものの構成・オプトインの設定方法（→
> [architecture/](../architecture/)、設定画面のヘルプ）。

## 文脈

セッションごとに git worktree を切って作業ディレクトリを隔離する機能（オプトイン）を入れた。
worktree の作成は、ディスク不足・ブランチ名の衝突・リポジトリでないディレクトリ・権限など、
実行時に失敗しうる。

改善計画書の該当節は、失敗時の扱いとして次の 2 つを**併記していた**。

- 「明示的にエラーを出したうえで従来挙動（共有ディレクトリ）へフォールバックする」
- 「サイレントフォールバックはしない」

この 2 つは両立しない。「明示エラーを出せばフォールバックしてよい」と読めば 1 つ目が通り、
「隔離すると言った以上そこへ落ちてはならない」と読めば 2 つ目が通る。独立検証がこの自己矛盾を
指摘し、実装前に確定が必要になった。

## 決定

**worktree の隔離に失敗したら、そのセッションの起動を中止する。共有ディレクトリへ
フォールバックしない。**

エラーはユーザーへ提示し、セッションは開始しない。

## 根拠

隔離を有効にしているユーザーが求めているのは「他のセッションと作業ディレクトリを共有しない」
ことである。失敗時に共有ディレクトリへ落ちると、**ユーザーが明示的に避けた状態へ、失敗を
きっかけに入る**ことになる。エラーを出していても、複数セッションが同じディレクトリで走り出す
という結果は同じで、そこから起きる破壊（同時編集・ビルド巻き添え・ブランチの取り合い）は
エラーメッセージでは防げない。

「隔離できないなら動かさない」方が、失敗の影響がその 1 セッションの起動失敗にとどまる。

## 結果

- 隔離が有効なセッションは、worktree を用意できなければ起動しない。
- **中止したのにエージェントが起動する経路が実在した**。復元経路の `makeRestoreErrorSession` が
  生きた `SpawnRequest` を保持しており、隔離を中止した約 150ms 後にエージェントが起動していた
  （静穏待ちで 6/6 再現）。本 ADR の決定を実装したことで初めて到達し露出した既存の潜在バグで、
  受け入れテスト `AcceptanceRestoreAbortNoSpawnTests` を凍結して塞いだ。
- 「中止」は隔離が**有効なとき**の話である。隔離を使わない既定の運用は従来どおり共有
  ディレクトリで動く（本 ADR はその挙動を変えない）。
