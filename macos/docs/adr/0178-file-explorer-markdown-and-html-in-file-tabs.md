# 0178: ファイルツリーはインスペクタのタブに置き、マークダウンと HTML は既存のファイルタブで表示・編集する

## 決定

要件と詳細設計は `specs/file-explorer-and-markdown-editing.md`。ここには決定と理由だけを残す。

1. **ツリーはインスペクタの新タブ（`InspectorTab.files`）**。新しいペインは作らない。
2. **ファイルを開く先は既存のファイルタブ（`ChildTab.file`）**。保存・競合・未保存確認は `FileTabDocument` の 1 系統だけにする。
3. **マークダウンはブロック単位で編集し、原文が正本**（ユーザー決定 2026-10-02）。編集を確定すると、そのブロックの元の行範囲だけを差し替える。
4. **描画は文書全体を 1 回解析してから、ノード単位で Markdown を再出力して描く**。
5. **パスの安全性は入口ではなく、共通の読み書き経路で保証する**（シンボリックリンクの解決後に作業フォルダ内かを毎回確かめる）。
6. **未保存・競合の判定はバイト比較**。BOM は読み込み時に覚えて保存時に戻す。
7. **HTML は JavaScript 常時無効・外部通信を遮断・独自スキーム `phlox-worktree` で worktree 内のファイルだけを配信**する。
8. **下書きはウィンドウ間で共有しない**。終了確認・削除確認は、アプリ全体の登録簿から全ウィンドウの未保存を集める。

## 文脈

- 既存のファイルタブには、シンボリックリンク経由で作業フォルダ外を読み書きできる・`String ==` が Unicode 正規等価で比較してバイト差を見逃す・保存で BOM が消える・終了時に未保存を確認しない、という欠陥があった（2026-10-02 のコードで確認）。新機能でファイルを開く入口が増えるため、先にこの欠陥を直す。
- ブロックの原文を個別に描画すると、別ブロックの参照リンク定義が解決できない・閉じていないフェンスに定義が吸い込まれる、という反例が Codex レビューで見つかった。

## 棄却した案

- ツリー専用の新ペイン: `PaneWidthPolicy`（左サイドバー・中央・インスペクタの 3 領域の幅を決める純関数）と既存の幅テストを作り直すことになる。
- 専用エディタ: 保存・競合・未保存確認を二重に実装することになる。
- WKWebView と JavaScript エディタでのマークダウン編集: 保存すると記法が書き換わる。
- 属性付きテキストからマークダウンを作り直す方式: 表・入れ子・front matter が失われる。
- 左右並列のプレビュー: 「描画した状態のまま編集したい」という要望を満たさない。
- HTML の `file://` 読み込みと外部リソースの許可: 作業フォルダ外のファイルや外部への通信を止められない。
- 下書きのウィンドウ間共有: 複数ウィンドウから同時に編集したとき、どちらが編集しているかを管理する仕組みが要る。

## 結果

- インスペクタの幅は最大 340pt のままなので、ツリーは狭い。子タブの分割は、中央の幅が 641pt 未満なら操作中のタブだけを表示する既存の挙動を維持する。
- 新しく `swift-cmark` に依存する（解析のため）。
