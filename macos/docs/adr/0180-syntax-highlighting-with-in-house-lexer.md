# 0180: ファイルのソース表示は自前の字句解析で色付けする

## 決定

2026-10-04 のユーザー決定。`ChatRenderKit.ChatCodeTokenizer` を拡張し、ファイルタブの `CodeTextEditor` に適用する。tree-sitter は導入しない。対象・色・受け入れ基準は [シンタックスハイライト仕様](../specs/syntax-highlighting.md) に置く。共有規則とファイルタブへの接続を実装し、検証結果は [作業記録 0040](../delivery/0040-syntax-highlighting-worklog.md) に記載する。

- 種類の判定と、言語ごとの字句規則を分ける。精度が必要になった種類だけ、後から色付け部品を差し替えられるようにする。
- プログラムに限らず、設定・マークアップ・データ・差分を扱う。判定できないテキストは本文色で表示する。
- チャットのコード表示・変更タブと字句規則を共有する。表示属性だけを付け、原文・保存・編集履歴を変えない。

## 文脈

ファイルタブの用途は「読んで少し直す」。キーワード・文字列・コメント・数値・タグ・キーなど、字句で判定できる色分けで十分と判断した。2026-10-04 のコードでは、チャットと変更タブは既に自前の部品を使う一方、`CodeTextEditor` は本文色だけで表示している。

[ADR 0030 §4](0030-transcript-eager-layout-and-one-way-composer-metrics.md) では、非同期の色付け完了で部品のサイズが変わる HighlightSwift を、同期・決定論的な `ChatCodeHighlighter` に置き換えている。これはサイズの揺れに対する防御策であり、CPU 暴走の真因は同 ADR §1 の遅延レイアウトだったという訂正も維持する。今回の背景計算も、文字の寸法を変えず前景色だけを反映する。

## 棄却した案

| 案 | 採らない理由 |
|---|---|
| tree-sitter | 構文の精度は上がるが、言語ごとの C の文法パッケージと色付け定義が必要になる。依存・ビルド時間・アプリサイズ・保守の増加を、今回の読み書き用途には見合わないと判断した。増加量の実測比較はしていない |
| Highlightr / highlight.js | 多数の言語を扱えるが、JavaScript の実行環境・定義・テーマ変換という別の経路が増える。既存の Swift の規則と入力欄の属性更新を共有する方針を優先する。導入試験はしていない |
| HighlightSwift の再導入 | ADR 0030 の予防方針を維持し、非同期完了によるサイズ変動を持ち込まない。現在の版で同じ問題が再現するかは未検証 |

## 結果

外部の色付け依存を増やさず、チャットのコード表示も同じ規則の拡張で良くなる。一方、言語ごとの規則とテストは自前で保守する。JS の正規表現と割り算、文字列に埋め込んだ式、シェルのヒアドキュメントなど、文脈で意味が変わる書き方の誤判定は受け入れる。構文エラー診断・補完・意味解析は対象外。

## 追記（2026-10-04）: Markdown ソースの見出しは等幅の太字にする

見本3cに合わせ、Markdown ソースの ATX 見出しだけは `NSTextStorage` のフォント属性を等幅の semibold にする（[シンタックス仕様 §4](../specs/syntax-highlighting.md)）。字幅・行間・保存本文・入力属性は維持し、フェンス内とブロック編集には適用しない。各バッチの更新をまとめ、本文へ戻った日本語の代替字体も太字を解除する。検証は [0041](../delivery/0041-leftover-polish-worklog.md) に記録する。
