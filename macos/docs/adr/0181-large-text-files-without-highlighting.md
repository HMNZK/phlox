# 大きいテキストの色付け・編集・閲覧の上限を分ける

## 決定

- 閲覧のみのソースでは、改行を除く10,000 UTF-16単位超の行を先頭10,000単位以内の書記素境界で省略し、「…（残り N 文字を省略）」をtextTertiaryで付ける（enも用意）。Nは省略した書記素数。しきい値はChatCodeTokenizerの色付け判定と共有する。表示用の文字列だけを作り、本文・BOM・読込バイト・外部変更の検出を変えない。コピー・検索は表示文字列を対象にし、帯には省略があるソース表示でだけ「長い行は省略して表示」を加える。編集可能な5 MB以下とHTMLレンダリングには適用しない。
- 色付け上限は1,000,000バイト、編集上限は5,000,000バイト、閲覧上限は20,000,000バイトとする。BOMを含むファイル全体のバイト数で判定し、WorkingTreeTextに集約する。5 MB超〜20 MBは色付けなしの閲覧のみ、20 MB超はData読込前に拒否する。
- 1 MB超は背景の色付け処理を予約せず、編集可能な文書の本文・undo・保存・バイト一致・競合検出を保つ。上限は読込時の制限であり、編集可能として開いた後の入力・保存をサイズで禁止しない。編集上限を超えて保存した文書は次の新規読込で閲覧のみ、閲覧上限を超えた文書は読込拒否になる。
- 本文は受け取ったStringをそのまま保持し、UTF-8への符号化は保存時に行う。同期・未保存判定はNSStringの同一性・長さ・非正規化比較を使う。保存競合は従来どおりディスクのバイト列で比較する。
- CodeTextEditorは最新の本文を読む／書く入口を保持し、Bindingの写しによる古い本文の同期を避ける。本文をビュー構造の比較対象にせず、SwiftUIによる全文の正規化比較を防ぐ。未保存判定は文書の版ごと、帯の色付け可否は版・BOM長ごとに一度だけ判定する。
- TextKitの非連続レイアウトを使い、色付けなし分岐の最後で文字形だけを準備する。貼付け・フォント変更・外部同期後も準備し、全文レイアウトは強制しない。行番号の索引は編集範囲前後の行だけ更新し、後続の位置を文字数差分でずらす。折返し・行間は保つ。
- 閲覧のみは既存NSTextViewのisEditable=falseを使い、選択・コピー・検索・スクロールを保つ。文書の変更・保存・上書き・dirty・未保存確認・undoを無効にする。外部変更は既存ソースと同じくタブを開き直して反映する。HTMLの安全なレンダリングと再読込は従来どおり残す。
- 変更パネルは同じ編集・閲覧上限を共有する。5 MB超〜20 MBは内容を閲覧、20 MB超は変更プレビューのみ。差分の色付けと500行単位のプレビューは維持する。
- Markdownの500 KB／2,000ブロックのソース固定を維持する。5 MB超もソース閲覧のみ。見本3lの構成を流用して上限数値を20 MBへ更新し、閲覧のみの案内は既存の帯を使う。

## 根拠

Apple M4 Pro・24 GiB、macOS 26.6.2。Release、実FileTabViewを画面外800×600 ptで描画する。先頭・中央・末尾で各25回の挿入とundoを行い、準備5回を除いた60回から入力→次描画のp95を求める。ディスク読込・dirty判定・SwiftUI更新・可視範囲の描画を本番の経路で測る。

入力→描画p95の判断用診断は、1 MB32.4 ms・2 MB40.1 ms・5 MB80.9 ms・10 MB149.8 ms・20 MB288.3 ms・実6.6 MB HTML991.6 msだった。入力→描画100 ms以内という目安を満たした最大の測定サイズは5 MBなので、5 MB超は閲覧のみとする。実6.6 MB HTML（128行目が改行を除き4,172,954 UTF-16単位。r4で実ファイルを再計数）を開くため閲覧上限は20 MBとする。生データは `.build/large-file-performance/document-r2-cached.json`。

r2の5 MB上限時点では、入力→描画p95が1 MB33.9 ms・2 MB41.2 ms・5 MB82.1 ms・実550 KB HTML32.0 msだった。r4の長行省略後の読込・初回表示・閲覧スクロールの測定値と最終検査結果は0043に記録する。

初回に開けたことを応答性の根拠にしない。長い段落は文字形の準備後もTextKitの組版が残り、ファイルサイズだけでは快適な入力を保証できない。文字形の準備は、準備済みのAppKit基準に対して貼付け・フォント変更・外部同期・1 MB境界通過後の入力が2倍（最低16 ms）を超えないこともReleaseで検査する。

## 検証と限界

- 10,000／10,001 UTF-16単位・サロゲートペア・結合文字・CRLF・複数長行、目印の色、表示文字列のコピー、本文とバイト保持・保存拒否、編集可能な長行を省略しないことをテストへ登録する。
- BOMの受渡し、1 MB・5 MB±1・20 MBと20 MB+1の境界、閲覧のみの入力・貼付け・保存拒否、選択・コピー・スクロール、改行・正規等価表現のバイト保持、外部変更後の開き直し、行番号、undo、競合、編集上限を超えて成長した後の二度の保存と閲覧のみでの再読込をテストへ登録する。
- 性能検査は実FileTabViewのdelegateを使う。代理delegateは削除した。編集可能な測定ファイルは入力→描画p95 ≤ 100 msを要求し、閲覧のみは開く時間と画面外スクロールのフレームp95・最大を記録し、実6.6 MBは初回を含む75位置の最大100 ms以内を要求する。色付けの既存13条件は別に検査する。実ファイル不在時のRelease文字形回帰は条件付きスキップとする。
- 画面外の写真、全数テスト、Debugビルド、UI build-for-testing、変異検査の結果は0043にまとめる。
- 実キー・ホイール・GPU合成・実HTMLレンダリングの時間、変更パネルの実画面の性能、ピークメモリは未検証。XCUITestの結果は作業記録0043に記録する。編集欄の破棄時は本文と組版を先に切り離す。非連続レイアウトのまま外すと、数十万行の文書で全文を組版し直して10秒以上固まるため（0043）。
