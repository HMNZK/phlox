# 0182: 元画像の受付上限と送信上限を分ける

## 問題

Composer・iOS・ControlServer は画像を各4MiB・合計8MiBに制限している。圧縮方式に左右されるファイル容量だけで拒否するため、画面写真をユーザーが手作業で加工する必要がある。

## 決定

- 元画像は1枚20,000,000バイト（20MB）・最大4枚・合計80,000,000バイトまで受け付ける。MBは10進で統一する。
- 送信用は1枚3,500,000バイト・最大4枚・合計14,000,000バイトまで。base64後は1枚約4.67MBとなる。これは接続先の最大値を主張するものではなく、旧送信経路より小さい保守的な運用値。
- 画像処理は共有ImageAttachmentKitで行う。ImageIOで容量・寸法・形式を確認してから画像を展開する。画素数は最大40,000,000、各辺は最大32,768を受付上限とする（展開後約160MB、1枚ずつ処理）。
- 制限内のPNG/JPEGは変更しない。送信容量を超えるPNGはまず同じ寸法のPNGへ再エンコードする。必要なら段階的に縮小し、透明部分を保持する。JPEGは品質0.9を下限として縮小する。HEIC等はJPEG（透明ならPNG）へ変換する。送信用寸法は各辺8,000以下。
- 送信処理を画面のメインスレッドから外す。入力・添付・モデルの変更をawait後に検出し、古い画像を送らない。失敗時は本文と添付を保持する。
- iOSはControl APIへ送る前に調整する。ControlServerは受信容量を独立に検査する。旧iOSとの互換性のため受信は各4MiBまで許し、合計は14MB。macOS側の送信前処理で各3.5MBへ調整する。HTTP bodyの16MiBは4枚分のbase64を収める24MiBへ変更し、HookServerには適用しない。
- 元画像は再送のため保持する。送信失敗で添付を消さず、既存の画像番号・Codex一時ファイルの寿命を維持する。

## 検証

容量境界・画素数・破損・透明PNG・HEIC・文字の画質・4枚同時をテストする。接続先ごとの変換・再送・画像番号・一時ファイルの検査を保つ。実送信とメモリ・処理時間の計測で運用値を評価する。CLIは手元でClaude Code 2.1.294 / Codex 0.161.0を確認した。API資料の上限をCLIの実証済み上限とは扱わない。

## 検証状況

実装済み。共有処理の7テストと関連パッケージのテストを実行した。6,331,070バイトの実画像4枚を各3,179,642バイトへ調整し、Claude Code / Codexへの実送信で枚数・文字・色を確認した。これは手元の確認であり、CLIへの実送信検査はリポジトリのテストには未登録。詳細・警告・未検証範囲は[作業記録](../delivery/0044-image-attachment-limits-worklog.md)を参照。
