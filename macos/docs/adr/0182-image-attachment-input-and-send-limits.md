# 0182: 元画像の受付上限と送信上限を分ける

## 問題

変更前のComposer・iOS・ControlServerは画像を各4MiB・合計8MiBに制限していた。圧縮方式に左右されるファイル容量だけで拒否するため、画面写真をユーザーが手作業で加工する必要があった。

## 決定

- 元画像は1枚20,000,000バイト（20MB）・最大4枚・合計80,000,000バイトまで受け付ける。MBは10進で統一する。
- 送信用は1枚3,750,000バイト・最大4枚・合計15,000,000バイト。base64後の各5MBはClaudeのBedrock/Google Cloud経路の仕様から導く。直接APIとCLIの実証済み上限は同一とは主張しない。仕様は[Claudeの画像資料](https://platform.claude.com/docs/en/build-with-claude/vision)（2026-10-08確認）。
- 画像処理は共有ImageAttachmentKitで行う。ImageIOで容量・寸法・形式を確認する。各辺8000pxという送信先の寸法上限を使い、最大画素数は8000×8000＝64,000,000。4000万画素という独立した受付上限は廃止する。入力4枚は1枚ずつ処理する。
- 制限内のPNG/JPEGは変更しない。容量超過のPNGは同じ寸法で再エンコードし、実際に透明な画素がなければ同寸法のJPEG品質0.95も試す。HEIC等はJPEG（透明ならPNG）へ変換する。容量のために縮小しない。収まらない場合は本文・原本を保持してエラーにする。JPEGによる画素の完全保持や可読性全般は保証しない。
- 送信処理を画面のメインスレッドから外す。入力・添付・モデルの変更をawait後に検出し、古い画像を送らない。失敗時は本文と添付を保持する。
- iOSはControl APIへ送る前に調整する。ControlServerは受信容量を独立に検査する。旧iOSとの互換性のため受信は各4MiBまで許し、合計は15MB。macOS側の送信前処理で各3.75MBへ調整する。HTTP bodyの16MiBは4枚分のbase64を収める24MiBへ変更し、HookServerには適用しない。
- 元画像は再送のため保持する。送信失敗で添付を消さず、既存の画像番号・Codex一時ファイルの寿命を維持する。

## 検証

容量境界・画素数・破損・透明PNG・HEIC・文字の画質・4枚同時をテストする。接続先ごとの変換・再送・画像番号・一時ファイルの検査を保つ。実送信とメモリ・処理時間の計測で運用値を評価する。CLIは手元でClaude Code 2.1.294 / Codex 0.161.0を確認した。API資料の上限をCLIの実証済み上限とは扱わない。

## 検証状況

実装済み。共有処理の7テストと関連パッケージのテストを実行した。6,331,070バイトの実画像4枚を各3,179,642バイトへ調整し、Claude Code / Codexへの実送信で枚数・文字・色を確認した。これは手元の確認であり、CLIへの実送信検査はリポジトリのテストには未登録。詳細・警告・未検証範囲は[作業記録](../delivery/0044-image-attachment-limits-worklog.md)を参照。
