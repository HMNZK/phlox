# ADR 0211: Ghostty をユーザー用ターミナルの表示エンジンとして採用しない

## 文脈

状態は **見送り**。2026-10-15 のユーザー判断として、Ghostty のコードを dev に入れず、表示エンジンは SwiftTerm だけを使う。調査・計測の結果を残し、SwiftTerm の改善を優先する。

目的は、ユーザー用ターミナル（下部パネルとターミナル子タブ）の表示エンジンに Ghostty を選べるようにし、描画性能と操作性を評価することだった。エージェント用端末は対象外とした。

## 試したこと

- 有志の `Lakr233/libghostty-spm` `2.2.2026101301` のビルド済みバイナリ経由で Ghostty を埋め込んだ。Zig の自前ビルドは行わなかった。
- PTY（シェルとの入出力）は Phlox が所有し、本家に無い `HOST_MANAGED` の改造を使って表示・入力だけを接続した。
- 日本語入力の受け付けは Phlox 所有の `NSView / NSTextInputClient` で自作し、確定文字・未確定文字・候補窓の座標を C API へ接続した。

詳細は [試作の研究記録](../research/ghostty-user-terminal-spike.md) に残す。試作時の ADR 0211〜0216 はこのツリーには持ち込まない。本 ADR の 0211 は、それらとは別の見送り判断である。

## 日本語入力の評価の訂正

試作中は日本語の確定文字の消失・重複を理由に一度見送った。しかし、`CGEvent.postToPid` の合成キーによる試験を既存の SwiftTerm に当てても同じ形で失敗し、この結果を Ghostty 固有の不具合とする評価は誤りだった。

入力の流れを記録した試験では、Phlox の境界での取りこぼし・二重送信は0回だった。人の手入力によるライブ変換と Space の候補選択は計8回すべて、確定文字が1回ずつ届き、Ghostty も合格した。記録の生データは残していない（要点は研究記録）。今回の見送りは日本語入力の試験失敗を根拠にしない。

## 性能の計測

2026-10-15 に同じ Debug ビルドで実機計測した。各エンジン 3 回の中央値［最小–最大］。負荷は `seq 1 1000000`、色付きの 52MB・40 万行のファイルの `cat`（太字・16 色・256 色・24bit の前景と背景）、`yes | head -2000000`。ウィンドウ 1400×900pt、端末領域 1123×236pt、既定のフォント。CPU とメモリは `ps` を 0.5 秒ごとに取り、「落ち着く」は瞬間の CPU が 5% 未満の状態が 2 回続いた時点。

## 決定と理由

Ghostty は採用しない。得られた利点は大量出力後の短い待ち時間、Option+← が効くこと、色付き出力後の余計な文字が出ないことだったが、次の欠点を引き受けるほどの差ではない。

- 試作では端末の可視テキストの VoiceOver 読み上げに未対応。
- 有志のパッケージと、本家に無い `HOST_MANAGED` の改造への依存が残る。
- 日本語入力の受け付けを Phlox が自作し、継続して保守する必要がある。

代わりに SwiftTerm の Metal 描画の試行、Option+←、色付き出力後の余計な文字を改善対象とする。この記録作業にはそれらの実装を含めない。

## 結果と再検討する条件

試作ブランチ `feature/ghostty-spike` のコードは dev に取り込まず、製品コードとして残さない。調査・計測と本判断だけを保存する。本作業では試作ツリーを読み取っただけで、ブランチの削除や Git 操作は行わない。

公式の埋め込み用の部品と IME 対応が提供された場合、または SwiftTerm の改善で限界が明確になった場合に再検討する。その際は VoiceOver、手入力の日本語確定、CPU と描画性能を改めて評価する。
