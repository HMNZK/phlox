# 自動整列とカスタム配置を分ける

## 背景

グリッドは保存済みの分割ツリーを描画する。セッション追加は最大ペインを分割するため、6セッションでも3列×2段には揃わない。
表示対象の絞り込みでは保存ツリーを刈り込むため、選んだセッション数だけで均等配置を作ることもできない。
一方で、ユーザーが調整した分割と比率は、絞り込みや再起動で失われてはならない。

## 決定

自動整列を新規利用時の既定とする。表示対象だけをサイドバー順で並べ、最小外寸540×440ptと8ptの隙間から列数と段数を決める。
列幅は均等とし、最終段の空きは直上のタイルを縦へ伸ばして埋める。5個・3列では③が2段分になる。
高さが足りない場合はグリッド全体を縦スクロールする。極端な狭幅では最小幅を守って横スクロールする。
寸法の基準と計算は[レイアウト要件](../specs/pane-layout.md)に置く。

自動配置は表示ID列と確定した利用可能領域から純粋に導出する。自動ツリーを保存したり、各更新元から再配置通知を送ったりしない。
利用可能領域とリサイズ中の状態はウィンドウごとに分離する。アプリはDashboardVMをウィンドウ間で共有するため、寸法をVMの単一値にすると別のウィンドウの配置まで変わる。
計算結果は既存の `PaneTree` とcanvas寸法で表す。描画、分割線、タイル移動、番号、キーボード操作は同じ形状を使う。

保存状態は自動とカスタムをenumで分ける。カスタムは全件ツリー、プリセット、canvasの下限寸法をまとめて持つ。
自動へ戻すときは直前カスタムを保持し、同じメニューの「直前のカスタムに戻す」で復元できる。
会話入力の取り消し操作とは接続しない。旧版の有効な保存ツリーはカスタムとして読み込む。
新形式は別キーで保存し、存在する新形式が壊れている場合は旧形式に読み替えない。

自動から手動へ移るときは現在の可視ツリーを起点にする。非表示セッションは別の枝へ保持し、刈り込み後の可視幾何と分割線IDを変えない。
canvas下限も引き継ぎ、長い自動配置を手動へ切り替えた瞬間に圧縮しない。
カスタム内の増減は既存の局所的な追加と除去を継続し、全体の自動整列はしない。

## 採らない案

- 自動とカスタムで描画方式を分ける案。形状、番号、隣接探索、操作時の変換が二重になる。
- 自動ツリーを観測状態として保存する案。表示選択、順序、所属、runtime snapshot、リサイズの更新元で同期規則を共有する必要がある。
- 非表示セッションを最大ペインへ足すだけで手動へ移る案。同軸の分割が平坦化されると、非表示を刈り込んだ後に可視比率が変わる。
- 固定寸法と隙間0で採番する案。空き段を吸収するためのweightを別の寸法へ当てると、同じ段のタイルが異なる高さと判定される。

## 影響

既存のカスタム配置を保持でき、自動整列へいつでも戻せる。分割ツリーとフラットなタイル描画は継続する。
自動から引き継いだカスタムcanvasは下限を保持するため、ウィンドウを縮めるとスクロールが生じる場合がある。
Dock、サイドバー幅、右インスペクター、下部パネルによって同時に表示できる列数と段数は変わる。
旧k×kの配置データ移行、一般的な配置操作の取り消し履歴、Redo、canvas寸法だけを編集する専用画面は追加しない。

## 検証

配置計算、モード遷移、保存形式、フィルタ、runtime snapshot、採番、キーボード操作とリサイズをパッケージのテストへ登録した。
SwiftUIの実ビューを画面外に描画する検査で、5個と6個のフルHD相当配置、狭幅、長いcanvasからの切り替えを確認する。
実メニューの選択はXCTestで検査する。NSMenuの追跡をSwift Testingのasync-main内で行うと、最終結果を出す前にrunnerが終了するため。
登録先は[構造の説明のテスト一覧](../architecture/session-pane-layout.md#テスト)に置き、実行ログと画像の計測は作業記録へ残す。
