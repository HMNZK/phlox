# ADR 0225: 送信の受付を画面同期から切り離す

## 問題

送信後に本文が薄く残り、入力欄がしばらく編集できなくなる報告があった。実行中サービスのsampleでは、画面状態の作成から呼ばれるCodexスキルの変更検出計算がメインスレッドを占有していた。画面側も送信の受付後に状態の取得と適用を待ち、その間は入力欄を無効にしていた。発生時と同時のsampleはなく、報告された2回の遅延への寄与率は不明である。

## 決定

`CodexSkillSelectionState.refresh()`がスキル一覧を取得し、ファイル一式の指紋をメインスレッド外で計算する。既存の世代番号と取消しを確認した後、一覧と指紋を一緒に公開する。計算中は読み込み中かつ古い状態として、スキル選択と送信を許可しない。`makeRuntimeSnapshot()`は確定済みの値を返し、ファイルを走査しない。

`.send`と`.sendControlSkill`に対する`.accepted`応答は、追加の画面同期を待たずに返す。受付済み本文は実行サービスが保持し、表示は既存の定期同期で反映する。それ以外の応答とコマンドは従来どおり状態の反映まで待つ。通信断と不正な応答を結果不明とする契約、結果不明時の自動再送禁止、受付後に失敗した入力の回収は維持する。

画面側の`inFlightText`は、画面から送った要求の受付待ちだけを表す。サービス内部のエージェント開始待ちは入力欄へ投影しない。受付後の同期や画面再接続で入力欄を再び無効にせず、次の下書きを編集できる。実行側の重複送信拒否と失敗入力の回収は維持する。

受付後の送信が拒否されたときは、入力欄をその本文だけで置き換えない。先の送信の失敗回収が並行して完了していた場合も、その本文と添付を先に残し、拒否された送信を後へ結合する。画像番号の書き換えには送信時点の添付一覧を使い、回収による番号変更と取り違えない。

スキルの共有ファイル、実行属性、欠損、シンボリックリンクの検査と送信直前の同一性確認は維持する。全セッション共通のコマンド順序は変えない。新しい通信形式やバックグラウンドの同期Taskは追加しない。

## 比較

一覧更新時に計算を完了する案を採用する。状態取得時に計算を予約する案は、読み取りから状態変更を起こし、新しいTaskの管理が必要になるため採用しない。選択したスキルだけを後から計算する案は、同期的な選択APIと通信方式まで変えるため採用しない。

同じ親モデルの独立した2コンテキストで比較した。異なるモデル系列でのcross-judgeはモデル設定がなく未実施である。最終実装は別コンテキストでまとめてレビューする。

## 検証

更新時に確定した指紋を画面状態が返すこと、次の更新で変更を検出すること、古い更新を採用しないことを検査する。画面状態の復号を保留したまま送信の受付が返ることを確認し、停止コマンドの既存同期待ちは維持する。標準品質入口と隔離した実アプリの送信・停止・再開・復元を実行する。結果は[作業記録](../delivery/0225-send-input-delay.md)へ記録する。
