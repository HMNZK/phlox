# 画像添付の品質と送信中の入力保持

## 修正対象

前回の再点検で挙げた4項目を扱う。送信に成功するためだけの過度な縮小、元形式への固定、容量値の根拠不足、iOSで送信失敗時に新しい入力を上書きする問題。

## 設計

- iOSはサーバーが送信を受け付けるまで本文・添付をクリアしない。成功時も、送信中に本文・添付が変わっていれば現在の入力を残す。失敗時は入力に書き戻さない。
- 画像は解像度を保持する方針を採用する。容量だけを理由に縮小しない。PNGを同じ寸法で再エンコードし、不透明なら同寸法のJPEG品質0.95も試す。透明PNGはPNGのまま。送信寸法8000pxを超える画像や、同じ寸法で容量内に収まらない画像は明確に拒否する。JPEGの画素が完全に不変とは保証しない。
- 送信容量はbase64後5,000,000バイトに収まる元バイト数3,750,000で計算する。4枚で15MB、base64で20MB。既存のControlServer body24MiBに収まる。本文や過去の履歴も含む接続先の32MB上限を、この制限だけで保証するものではない。
- 元画像の画素数制限は送信可能な最大寸法8000×8000から64,000,000画素を導く。4000万画素での拒否を解消し、8000×6000の48MP画像を受け付ける。処理中のバッファ数によるピークメモリは計測で別途確認する。
- 20MB・4枚は今回の受付要件。送信上限と寸法は接続先の仕様・経路の制約と区別する。APIの仕様をCLIの実証済み上限とは扱わない。
- [Claudeの画像仕様](https://platform.claude.com/docs/en/build-with-claude/vision)を2026-10-08に確認。各辺8000px、直接APIの画像上限10MB（base64後）、Bedrock/Google Cloudは5MB（base64後）。32MBのリクエスト上限は画像以外の本文・履歴も含む。

## 検証計画

- iOSの送信をテスト側で一時停止し、その間の本文・添付の変更後に成功／失敗を返す。新しい入力が消えないことを検査する。
- 実画像で解像度・透明部分・送信容量・形式選択を検査する。48MPと80MBの入力に対する処理時間・プロセスメモリを手元で計測する。
- 設定は既存のSwiftパッケージテスト、iOSのraw-value lint、XcodeGenのmacOS/iOSビルド。テストはcompact-test経由。macOSはrun-swift-tests.shを使う。

## 実装結果

1. iOSの失敗時の本文・添付の書き戻しを廃止した。受付まで入力を残し、成功時も途中の編集を上書きしない。編集の回数も確認するため、削除して同じ本文を打ち直した場合も消さない。テスト側で送信を一時停止し、本文・添付を変更してから成功／失敗を返す検査を追加した。
2. 容量のための段階的な縮小を廃止した。小さいPNG/JPEGは原本のまま、大きいPNGは同じ寸法のPNGへ直接再保存する。不透明な画像は同寸法のJPEG品質0.95も試す。透明な画像はPNGで保持する。容量や送信先の寸法に収まらない場合は、原本・本文を残して切り出しを案内する。
3. 20MB・4枚は受付要件として保持し、送信容量をbase64後5MBから各3.75MBへ導いた。送信寸法各8000pxから64MPを導き、8000×6000の48MP PNGをテストに登録した。これは最適値全般やCLI/APIの普遍的な保証ではない。
4. 日英のエラー文言を具体的な制約と対処へ変更し、画質全般を保証する表現を取り除いた。

PNGの直接再保存で収まる場合は、全画素の透明度検査を省く。RGBA8で透明度を調べる場合も既存の画素列を使い、巨大な検査画像を追加で作らない。16bitで透明度を持つ画像は8bit化で見落とさないよう保守的にPNGを選ぶ。

### 実送信と負荷（手元で実行、リポジトリのテストには未登録）

- Claude Code 2.1.294 / Codex 0.161.0へ4枚を送信し、枚数・見出し・18pxの英字・24pxの日本語・赤い図形を正しく読めることを確認した。1,800×1,400のPNG各6,346,075バイトを、寸法を変えずJPEG各2,325,259バイトへ変換した。
- 各画像へパディングを付けて3,750,000バイト（base64後5,000,000バイト）×4枚でも両CLIへ送信した。同じ文字・枚数・色を確認した。この検査は新規会話であり、過去の大量の画像を含む履歴の送信上限は未検証。
- 48MP（8,000×6,000）の単色PNGを各20MBへパディングし、4枚・80MBの元画像を同時に保持した。画像生成を別プロセスで済ませ、準備プロセスだけを`time -l`で計測した。
- 修正途中は最大RSS 1,141,981,184バイト・16.363秒。PNG直接再保存を先に行う修正後は291,291,136バイト・1.369秒、出力は各851,835バイト。単色の合成画像を使った測定であり、あらゆる写真やiPhone上の最大メモリを証明しない。
- JPEGによる画素の完全保持や、あらゆる文字の可読性は保証しない。容量に収めるため解像度を下げることはない。

### 失敗・警告

- 初回はCoreGraphicsのSwift初期化子が非nullableの色空間を要求するためコンパイル失敗。RGBA8での検査へ直し、最終的には通常のRGBA8画像の既存画素を直接走査する方式にした。
- 一度、既存`lineLocalScansStayLinear`の2秒上限に対し3.916秒となった。48MPの画素列を毎回生成する重いテストと並行負荷があった。実際の48MP PNGをテスト資源として保持し、テスト中の巨大な配列生成を除いた。時間上限・期待値は変更せず、再実行で588件成功した。
- 資料の更新時にADRのファイル名を誤りFileNotFoundErrorが発生。実在する0042を確認して更新した。
- 既存警告として、DashboardViewのViewBuilder、PTYKitの非推奨init(cString:)、TerminalUIの非Sendableコールバック、iOSの到達しないdefault・MainActor呼び出し・UIテストの非MainActor座標操作、AppIntentsなしのメタデータ抽出スキップが残る。Codexの標準エラーには通常の`Reading additional input from stdin...`が出た。
