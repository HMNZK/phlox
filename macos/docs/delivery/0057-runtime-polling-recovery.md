# 読取タイムアウト後の画面更新

## 症状と確認範囲

macOS の画面で回答が更新されず、追加送信すると以前の回答が現れる報告を扱う。
開始時の `SessionRuntimeClient.startPolling` は busy 以外のエラーで監視を終了する。
`command` は送信後の snapshot を別途取得するため、この終了後も追加送信で表示が更新される経路がある。
最初のタイムアウトの原因は未特定であり、この修正では断定しない。

## 修正の受入条件

一時的な読取タイムアウトの後、追加送信や手動再接続なしに新しい snapshot を表示する。
監視はクライアントの単一 Task が所有する。再試行は待機を挟み、同時実行やキューを増やさない。
disconnect と監視の再開始は旧 Task を取り消す。認証、互換性、応答形式の異常は再試行の対象に広げない。
送信コマンドを自動再送しない。

## 検証計画

修正前にタイムアウトを起こして監視停止を再現し、修正後に同じ条件で自動表示を確認する。
回帰テストは自動復帰、繰り返す障害の待機、取消し、監視の置換、致命的エラーと送信回数を扱う。
独立した差分とシナリオのレビューを記録し、共通マージの品質入口で検査して Dev に統合する。
通常アプリの再起動、差替え、main 統合、push と公開は対象外。

## 実施結果

修正前は回帰テスト10関数中4関数が失敗した。実 HTTP の読取タイムアウト後、40秒の観測中に次の GET と表示適用がなかった。
修正は既存の監視 Task 内に9行を追加し、`URLError.timedOut` だけを再試行する。
待機は1、2、4、8秒と増え、上限8秒で継続する。取得と表示適用が成功したら1秒へ戻す。
別の Task、公開設定、送信コマンドの再送は追加しない。既存の取消しと致命的エラーの終了経路を維持する。
修正後、標準入口経由の AppBootstrap 226テストが成功した。追加の回帰テストは10関数、HTTP状態の引数を含め12ケースである。
実 GUI の比較、独立シナリオレビュー、統合候補の品質検査は、この時点では未完了。
