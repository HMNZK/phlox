# 本文取得エラーの意味を保ち、更新後の会話表示を復旧する計画

タスク一覧の更新で古い行が消えても、会話の表示更新を続けられるようにする。正常な消失と不正な要求を区別し、通信、参照の失効、画面の復旧、エラーの寿命を一つの修正単位として扱う。

この文書は修正計画。調査対象は `dev` の `3052477f`。2026-11-11 に Claude Opus 5.5 の敵対的レビューを受け、条件付きだった画面側の修正と検証条件を具体化した。同日、ユーザーの実装指示を受けて修正に着手した。実行結果と未検証範囲は [作業記録](body-content-recovery-worklog.md) に記す。

## 計画を読む

対象読者は Phlox の実装とテストを担当する開発者。既存の実行サービスと画面の分離を知っている前提で書く。
実装時は下の手順を順番に進め、観測結果と終了コードがそろってから完了にする。
判断の中心は「更新は正常」「通信で意味を失わない」「復旧でも整合性と上限を守る」の三点。

## 守る条件を先に固定する

1. 本文とタスク一覧は取得中にも変わる。存在した行や作業が消えることを、ユーザーの入力ミスにしない。
2. 取得参照は永久に有効な約束ではない。実行、対象、構造の版、境界 ID を持つ参照として検証する。
3. 同じ失敗は、サービス内でも HTTP 通信後でも同じ意味を持つ。表示文言からエラーの種類を推定しない。
4. 正常な消失だけを、その消失を扱える呼出元で回復する。認証失敗、不正要求、通信失敗を成功に変換しない。
5. 更新は整合する範囲を一括適用する。古い版の詳細を混ぜず、失敗時は直前の表示と再試行手段を残す。全文再取得や無制限の再試行で回避しない。
6. 取得の成功と失敗には寿命がある。終了した実行、古い画面、新しい表示や操作に追い越された要求の結果で、現在のエラーを追加・消去しない。
7. カーソルの対象範囲が縮小・並替え・置換されたら、その範囲の構造版を進める。純粋な末尾追加や既存項目の本文更新だけでは、有効な過去の境界を失効させない。

上流の Codex 計画通知には永続するステップ ID がない。現在の行 ID は位置と文言から作られ、改名や挿入で旧行がなくなる。この制約の下では、推測でタスクを同一視するより、消失を正しく処理する方が確実である。

## 修正を順番に進める

### 1. 仕様と失敗する回帰を先に用意する

- [ ] `docs/specs/independent-session-runtime.md` に、下表の本文取得エラーと新旧版の保証範囲を記す。既存 ADR を書き換えず、新 ADR で ADR 0231 の復旧契約を通信境界まで明文化する。
- [ ] `SessionRuntimeTransportTests.swift` に実サービス側 transport と実 client を通す回帰を追加する。`notFound` が同じ型で呼出元へ届くこと、既存の `invalidRequest` と `staleContent` を取り違えないことを検証する。
- [ ] AppBootstrap の結合検査では実 source、transport、client を接続し、削除した行・作業・境界と縮小後のカーソルでエラーの往復を確認する。画面側の競合検査は SessionFeature 内で行い、製品の全配線は隔離アプリで通す。テストのために製品 API の可視性を広げない。
- [ ] `SemanticChatReadTests.swift` と既存の構造検査に、公開入口から本物の続きのカーソルを取得してから件数を減らす回帰を追加する。カード行、カード内の集約作業、入力がない集約作業、入力はあるがカードがない集約作業を検査する。期待値は `staleContent` とする。純粋な追加と本文更新では旧カーソルの有効性を維持する。
- [ ] `RuntimeReadTransactionTests.swift` で、取得を保留して背景更新・新しい操作・実行切替を先に完了させ、その後に旧要求の成功・失敗を返す。画面へ渡す表示が古い結果で変わらないことを検査する。既存の保留ハーネスを使い、固定スリープでは順序を作らない。
- [ ] 同じ構造版の範囲外カーソル、負の位置、別対象のカーソルは `invalidRequest` のまま拒否されることを確認する。

| 本文取得の状態 | サービス内の意味 | HTTP | client が復元する意味 |
|---|---|---|---|
| 指定した行・作業・項目が存在しない | `notFound` | 404 | `notFound` |
| 正当に発行した参照の構造版・境界が古い | `staleContent` | 412 | `staleContent` |
| 位置が負、対象が違う、順方向の続き取得で現在版の位置が範囲外 | `invalidRequest` | 400 | `invalidRequest` |

既存の認証、応答容量、混雑の 401・413・503 は変更しない。404 を `notFound` に復元するのは `session-content` の取得に限定する。成功応答と要求の形式は変えない。現在版の範囲外を 400 とする規則は `nextStart` を使う行一覧と集約詳細の順方向取得に限り、他のページで境界が見つからない場合の既存の 412 は維持する。

HTTP 404 は対象セッション全体の不存在も表しうる。項目の正常な消失として回復する前に、404 の後で親セッションの存在と実行 ID を確認する。古い overview や、404 より前の取得成功だけを根拠にしない。親の不存在・実行の切替を行の削除として成功へ変換しない。

### 2. 意味が失われる最初の箇所を直す

- [ ] `SessionRuntimeContentError` を捕捉・比較する呼出元を、semantic 取得、従来の本文取得、全文断片、補助表示、端末表示に分けて監査する。404 化による差分を下の監査表と照合する。
- [ ] `SessionRuntimeTransport.swift` の要求処理で、`SessionRuntimeContentError.notFound` を 404 に対応させる。その他の例外を一律 404 にしない。
- [ ] `SessionRuntimeClient.swift` の応答処理で、`session-content` の 404 を `notFound` に戻す。400 を消失とみなさず、エラー文言も解析しない。
- [ ] `RuntimeChatReadIndex.swift` の `nextStart` を、対象と負の位置、構造版、現在の範囲、境界 ID の順に検証する。古い版のカーソルでは、件数の縮小で位置が範囲外になっていても `staleContent` を返す。同じ版の範囲外は `invalidRequest` を維持する。範囲確認前に配列を参照しない。
- [ ] カードのない集約作業で構造版が定数 `1` になる経路をなくす。既存の `Action` にその範囲の構造版を持たせ、再構築時の境界の維持と破壊を判定する。カーソルの生成と検証は同じ版を使う。カード付き応答の一括適用に使う版は維持する。保存形式や wire のフィールドは増やさない。
- [ ] 手順 1 の回帰を再実行し、修正前の失敗と修正後の成功を記録する。

`SessionRuntimeContentError` には必要な種類が既にある。新しいエラー型、応答の `code` フィールド、プロトコル版、機能フラグは追加しない。HTTP ステータスで既存の区別を保存できる。

### 3. 失効した参照から復旧し、古いエラーを残さない

- [ ] `refreshedRuntimeEntries` と `refreshedRuntimeActionItems` の既存処理を使う。手動の境界だけが消えた場合は対象を一度だけ再確認し、行・作業自体が消えていればその詳細だけを除外する。
- [ ] その除外を公開する前に、404 後の親の再確認を同じ取引で共有する。既存の有限な末尾取得でセッションと実行を確認し、影響するカードも現行の構造版と照合する。親セッションが消えた場合は失敗として保持し、旧表示を部分的な成功へ置換しない。セッションは残りカードだけが消えた場合は、取引を失効させて次の背景更新でカードのない現行ページを取得する。
- [ ] 残る行の詳細、手動の表示位置、新しい操作を保持し、背景更新の最後にまとめて公開する。全キャッシュの破棄や、詳細を一度空にする処理を追加しない。
- [ ] `RuntimeStatusCardPresentation.perform` で成功・失敗を画面へ適用する前に、実行 ID、画面の epoch、カード・対象の識別、構造版、操作の順序を照合する。本文更新や単なるキャッシュ差替えで進む `contentRevision`・`RuntimeCardReadCache.version` だけを、要求の寿命に使わない。背景更新や新しい操作で不要になった要求の失敗を、現在のカードへ書き込まない。古い成功で新しいエラーを消さない。取消しを本文エラーにしない。
- [ ] エラーは対象と取得操作の世代に対応させる。その対象の新しい取得または背景更新が成功して表示を公開した時点で、過去のエラーを消す。別の対象で起きた新しい失敗は消さない。本文が流れ続けても、有効な再取得が成功できる条件を保つ。
- [ ] 「再試行」と「最新の作業に戻る」を、通常の取得と同じ成功・失敗処理へ通す。現在は直接 `loadRuntimeCardEntries` を `try?` で呼び、成功してもカードのエラーを消さない。手動の再取得は、取得済みなら省略する初回取得のガードを通さない。
- [ ] 明示的な追加取得で `staleContent` を受けたら、古いカーソルを再送せず、既存の `needsContentCatchUp` と内容再同期へ接続する。同時の失効は一つの再同期へまとめる。対象が消えた `notFound` も、現在の取得文脈で正常な消失と確認できる場合だけ同じ復旧へ流す。無関係な失敗は表示する。
- [ ] 復旧取引がもう一度 `staleContent` になったら、直前表示を保持して次の定期更新を待つ。再失効だけを新しい表示エラーにしない。現在の catch-up の終了処理は `needsContentCatchUp` が立つと即時再予約するため、待機をこのフラグの再設定だけで実装しない。同じ取引からの追加要求・即時再予約はゼロにする。新しいタイマーは作らない。
- [ ] 再失効以外の失敗では直前表示と再試行手段を残す。同じ失敗を理由に自動復旧を再帰的に予約しない。背景更新が途中で新しい手動操作に追い越された場合は、その操作を優先する既存の制御を維持する。
- [ ] 過去表示の起点を背景更新する途中で、その入力・項目自体が消えた場合は、既存の末尾取得へ一度だけ戻す。成功したページと同時に末尾追従・起点を更新し、次回も消えた起点を要求する状態を残さない。失敗時は旧表示とエラーを保持する。ユーザーが明示した存在しない移動先は成功へ置き換えない。
- [ ] カード外の集約作業でも、境界だけの消失、作業全体の消失、古いカーソルの失効を区別する。`RuntimeChatTranscriptView` の既存の取得世代検査と境界再取得を使い、失効時だけ新しい参照へ戻す。

画面側の修正は必須とする。新しいレイアウト、操作、汎用 retry 機構は追加しない。404 往復だけの成功や、エラーを隠すだけの変更は完了と認めない。

## 受入条件を照合する

| 条件 | 外から確認する結果 | 検証箇所 |
|---|---|---|
| 行を開いた後にタスクを改名・削除・挿入する | 現行行と新しい出力が表示され、消えた行の詳細と誤った本文エラーが残らない | 実 transport を通す投影モデルの結合検査、隔離アプリ |
| 手動表示の境界項目だけが消える | 生存する行・作業を再確認して表示する。対象全体を欠落扱いにしない | 既存の境界削除回帰 |
| 行や集約作業自体が消える | 消えた詳細だけを除外し、残るカードを公開する | 既存の削除回帰と通信結合検査 |
| 行数・集約詳細が縮小し、発行済みカーソルを送る | `staleContent` になる。古いページを現在版へ混ぜない | `SemanticChatReadTests` |
| 現在版の範囲外・負の位置・誤った対象を送る | `invalidRequest` として失敗する。成功や消失へ変えない | サービス側と通信の回帰 |
| 明示的な追加取得と削除が重なる | 現行カードへ戻り、新しい操作を古い応答で上書きしない。エラーが恒久的に残らない | 結合検査、隔離アプリ |
| 旧要求の失敗が、新しいカード・操作・実行の公開後に届く | 新しい表示に古いエラーを書き込まない。旧成功でも新しい失敗を消さない | 保留を使う投影検査 |
| エラー後の再試行が成功する | 新しい詳細が表示され、同じ背景版でもエラーが消える。もう一度背景更新しても戻らない | 投影検査、AX |
| 出力追加中に再試行する | 本文更新だけで有効な要求を失効させず、新しい取得の成功・公開で過去の対象エラーを消す | 保留と連続更新を使う投影検査、AX |
| 一度の再同期中にも構造が変わる | 旧表示を保持し、追加要求・即時再予約・新たな stale エラーを出さず、次の定期更新の成功で現行表示へ戻る | 保留を使う投影検査 |
| 行の取得中にセッションが削除される・実行が切り替わる | 行の消失と誤認して部分的な成功を公開しない。旧実行の応答を新実行へ適用しない | 実通信の結合検査、投影検査 |
| 過去表示の起点自体が消える | 背景更新では末尾と追従状態を同時に確定する。次の更新でも消えた起点へ戻らない | 投影検査、隔離アプリ |
| カードのない集約作業の範囲が縮小する | 旧カーソルは位置にかかわらず失効する。本文更新と純粋な追加では有効な境界を保つ | サービス側と通信の回帰 |
| 401・通信失敗など、正常な消失以外が発生する | 旧表示を保持し、失敗と再試行手段を示す | 既存の通信・投影回帰 |

巨大履歴の応答 256 KiB、1 ページ 50 項目、カード行 8 本、画面の詳細キャッシュ 4 MiB という既存の上限を維持する。全文取得を自動復旧の前提にしない。性能向上は本計画の完了条件にせず、取得量と復旧の完了を確認する。

AX は既存のカード識別子を範囲にし、現在の行・追加出力の存在と、エラー文言・再試行表示の不在を合わせて確認する。エラー専用の識別子が存在するとは仮定しない。画面が空だからエラーがない、という成功判定にしない。

### 取得量と復旧の終点を記録する

- 再同期の完了を待った時点で、現行の行と追加出力が表示され、会話全体と対象カードに古いエラーがないことを確認する。次の背景更新後にも成立することを検査する。
- 同一の取得世代で失効した明示要求は一回だけとし、同じカーソルの再送はゼロにする。同時の失効から始める再同期は一取引までとする。HTTP 503 の既存の期限付き再試行は別に記録する。
- 一取引で更新するカード数を C、取得済みまたは画面から取得を要求して失敗した行詳細を E、同様の集約詳細を A とする。行の取得は最大 3C、行詳細は最大 2E、集約詳細は最大 2A の論理要求に収める。追加は手動境界と親カードの再確認に限る。404 後のセッション再確認に使う末尾取得は一取引で一回までとし、同時の消失で共有する。閉じたまま未要求の詳細と全文断片を自動で取得しない。
- API 結合検査では実 HTTP 応答の status と client が返す型を同じ要求に対応付ける。投影検査では loader 境界の論理要求を記録する。実アプリでは同じ fixture の遷移番号、AX の最終状態、runtime の実行世代・bundle の識別値を保存する。

## 新旧版の保証範囲を区別する

| 画面 | 実行サービス | 保証と制約 |
|---|---|---|
| 修正版 | 修正版 | 型を保つ取得と更新後の復旧を保証する |
| 修正版 | 旧版 | 旧サービスの 400 から消失と不正要求を区別できない。消えた詳細を保持する限り本文更新全体が繰り返し失敗し、新出力も止まり得る。再発防止の修正保証は届かない |
| 旧版 | 修正版 | 404 は従来の一般エラー表示になる。接続と通常取得を維持し、新しい自動復旧は保証しない |
| 旧版 | 旧版 | 従来の挙動が残る |

実行サービスはアプリ内容のハッシュごとに保存した bundle で動く。画面の更新・再接続だけでは既に稼働しているサービスは置き換わらない。`supportsChatReadModel` は今回の修正対応を識別する印ではない。

この計画の実行にも、利用中サービスの終了や差し替えは含めない。稼働環境へ修正を反映するときは、全セッションを安全に終えられる時点と保存確認を別途そろえる。既存サービスの停止が必要な操作は、その段階で明示の承認を得る。lease や discovery を削除して旧サービスを迂回しない。

### コードの完成と利用環境での解消を分ける

コードの完成は、修正版同士で受入条件と品質ゲートが通り、混在時の制約も隔離環境で確認できた時点とする。利用環境での解消は、その後の安全なサービス切替と接続先の確認を終え、同じシナリオが通った時点とする。

混在時に画面を再生成するなどの操作で一時的に解消する可能性はある。「サービス置換までどの操作でも絶対に回復しない」とは断定しない。識別できない 400 を無視して部分表示を公開する緩和策は、整合した旧表示を残す契約に反するため採らない。

## 付録 A. 確認した事実と限界

2026-11-11、実行中の Phlox 1.14.8 build 52 に読み取り専用で問い合わせた。画像の画面文言は「本文の取得位置が不正です。」である。同じ会話の同じ入力区間で、現在のカード行取得は HTTP 200、画像にある旧タスク 4 行の取得はすべて HTTP 400 だった。通信の失敗本文は「指定された本文が見つかりません。」だった。画面の文言と通信の本文を区別する。

調査記録は作業 worktree の [.verification/body-content-recovery-plan-20261111/observed-evidence.json](../../../.verification/body-content-recovery-plan-20261111/observed-evidence.json) に保持する。Git には追加しない。当時の画面内部のキャッシュは取得しておらず、この実測だけで画像が出た瞬間の全経路を確定したとは扱わない。

`SessionRuntimeTransport.swift` は `notFound` を既定の 400 にし、`SessionRuntimeClient.swift` は本文取得の 400 を `invalidRequest` にする。一方、投影モデルの `refreshedRuntimeEntries` と `refreshedRuntimeActionItems` は `notFound` を受け取れば削除を正常に処理する。この意味の消失はコードと実通信の双方で裏付けられている。

追加で、`RuntimeChatReadIndex.nextStart` は現在の件数による範囲検査を構造版の検査より先に行う。更新で件数が減った正当な旧カーソルを不正要求へ分類しうる。これはコードから確認した同種の問題であり、画像の失敗原因として実測したものではない。

既存の削除復旧テストは loader からサービスの関数を直接呼ぶため、HTTP による型の消失を通らない。既存の通信テストには `staleContent` と `invalidRequest` の往復があるが、`notFound` の往復がない。

## 付録 B. 採らない案と残す制約

| 案 | 採らない理由 |
|---|---|
| エラー文言だけを変更する | 削除を扱う復旧処理へ届かず、更新失敗が残る |
| 400 をすべて `notFound` にする | 本当の不正要求まで消失扱いになる |
| 日本語メッセージを比較する | 表示文言を通信契約へ昇格させ、翻訳や文言変更で壊れる |
| 応答へ新しい `code` を加える | 既存 HTTP ステータスで必要な意味を保てる。旧サービスの識別不能も解決しない |
| タスク ID を全面的に作り直す | 上流に永続 ID がない。改名と別タスクを確実に区別できず、今回の通信欠陥も残る |
| 全文再取得、全キャッシュ破棄、無制限再試行 | 有限取得・整合した表示・新しい操作の優先を損なう |

改名前後のタスクを同一視して開閉状態を引き継ぐ保証は追加しない。容量上限でも `invalidRequest` を返す経路は存在するが、今回実測した消失とは別の問題である。容量分類の全面変更は本修正へ混ぜず、既存の容量保護を維持する。

`Action.contentRevision` をそのまま構造版に使う案も採らない。既存項目の本文更新だけで版が変わり、有効な過去の境界まで失効するためである。範囲の縮小と本文更新を同じ変更として扱わない。

## 付録 C. 資料との不整合と参照先

- [ADR 0231](../adr/0231-semantic-chat-read-model.md) は所属しない項目を `notFound` と定める。内部の取得処理は守っているが、HTTP 境界では `invalidRequest` になる。仕様の弱体化ではなく、通信実装を既存の意味へ合わせる。
- ADR 0231 の構造版・境界 ID の検証方針に対し、`nextStart` は件数縮小を先に不正位置と判断する。仕様へ失効と不正入力の判定順序を明記し、検証を緩めずに実装を合わせる。
- 同 ADR の古い応答を混ぜない方針に対し、カードの取得エラーには実行・画面・カードの新旧検査がない。またカードのない集約の版が定数になり、範囲の縮小を表せない。これらも同じ契約違反として修正する。
- 同 ADR の有限取得・一括適用・手動操作の優先は維持する。
- [独立実行サービスの仕様](../specs/independent-session-runtime.md)、[ADR 0230](../adr/0230-bounded-runtime-overview-and-session-content.md)、[意味単位の取得の既存作業記録](0231-semantic-chat-read-model.md) を実装前に確認する。
- 隔離実行と画像取得は [Release と Debug の併存手順](../guides/running-release-and-debug-together.md) と [デスクトップ UI の検証手順](../guides/vision-testing-desktop-ui.md) に従う。
- 計画は単一の不具合修正を対象にする。複数 PR・常駐ループ・クラウド VM を前提にする pstack の長期計画ひな形と `check-plan.mjs` は対象外。文書の差分と相対参照を検査する。

## 付録 D. HTTP 404 化の影響を呼出元で確認する

| 取得の群 | 現在の呼出元と変更後に確認すること |
|---|---|
| semantic の行・作業・境界 | 投影の `notFound` 復旧へ届く。明示操作の失効は一度の再同期へ接続する |
| semantic の背景表示の起点 | `refreshedRuntimeWindow` は起点消失を捕捉しない。背景更新だけ末尾へ復帰し、起点の変更も一括確定する |
| `chatTail`・`chatBefore`・`pending`・端末表示 | 対象セッションの消失は従来の一般エラーから型付き消失へ変わる。正常取得と既存の stale 処理を維持する。semantic の子項目取得でも同じセッション消失が起こるため、子の 404 だけで正常な行削除と決めない |
| `itemChunk`・`approvalChunk` | 項目の消失を型付きで返す。欠けた断片を完全な本文・承認内容として確定しない |
| `chatPresentation` | `ChatSessionViewModel` は `invalidRequest` で失敗 revision を記録するが、`notFound` は別の経路になる。真の不正要求では抑止を維持し、消失後に同じ revision の再取得が可能であることと、同一更新中に再試行ループを作らないことを検査する |
| カード外の command group | `RuntimeChatTranscriptView` の境界再取得が有効になる。境界だけの消失と群全体の消失を区別し、古いカーソルでも復旧する |

製品の配線は `macos/App/DesktopCompositionRoot.swift` の `dashboard.runtimeContentLoader = { try await client.content($0) }`。通信の意味を別の型へ変換する処理は、この接続にはない。

## 付録 E. Claude の指摘をどう反映したか

[Claude Opus 5.5 のレビュー原文](../../../.verification/claude-plan-review-20261111/claude-review.md) と、コードとの照合結果は作業 worktree の `.verification/claude-plan-review-20261111/` に保持する。初回の読取ツール付きレビューは 360 秒で結果を返さず終了した。完成したレビューは、計画全文と行番号付きのコード抜粋を渡した、ツールなしの別実行である。リポジトリ全体の独立探索や実機検証とは扱わない。

| 指摘 | 採否と計画の変更 |
|---|---|
| 遅い取得失敗と再試行後のエラー残留 | 採用。世代検査と手動再取得の共通処理を必須にした。既存のボタンは行ではなく行詳細を直接再取得していることも確認した |
| stale 分類後の復旧が未定 | 採用。既存の catch-up は `needsContentCatchUp` を立てなければ動かない。失効からの一回の再同期を必須にした |
| 新 GUI と旧 runtime で更新が止まる | 採用。実害と、コード完成・利用環境での解消の違いを明記した。「置換まで絶対に回復しない」という断定は根拠不足として採らない |
| 他 target と背景起点の消失の見落とし | 採用。影響監査表を追加し、背景起点の一度の復帰を修正範囲へ含めた |
| 定数版では同じ版の失効を判別できない | 採用。カードのない集約の構造版を修正対象にした。提案された「範囲外をすべて stale にする」「続きの発行をやめる」は不正入力の検出と既存のページ送りを損なうため採らない |
| 結合検査の可視性と観測条件が曖昧 | 採用。実通信、投影の競合、実アプリの三層に分けた。公開の投影初期化・loader・`refreshRuntimeContent` は存在し、パッケージ間の試験が不可能と確定したわけではない。製品 API の拡張は不要。要求量と AX 観測を具体化した |

[改訂版の再レビュー](../../../.verification/claude-plan-review-20261111/claude-recheck.md) は、改訂計画と裏取りした事実を対象にした。ソースの再探索は行っていない。追加の三指摘も反映した。

- 本文更新だけで要求が失効し続けないようにし、成功した対象のエラーを消す責任を明記した。
- 復旧中の再失効は次の定期更新へ回し、既存フラグによる即時再予約ループを禁止した。
- セッション全体の不存在と子項目の消失を区別するため、404 後の親の有限な再確認を必須にした。カードだけが消えた場合と親セッションが消えた場合も区別した。

Claude の再レビュー判定は「なお要改訂」であり、上記を反映した最終稿に対する承認結果ではない。最終稿の反映確認は計画作者が行う。実装・実走前の製品品質を保証する記録ではない。
