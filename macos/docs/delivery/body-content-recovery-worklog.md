# 本文取得の分類と失効復旧の修正記録

作業ブランチは `body-content-recovery-plan-20261111`、起点は `dev` の `3052477f`。仕様は [ADR 0232](../adr/0232-runtime-content-reference-recovery.md)、受入条件は [修正計画](body-content-recovery-plan.md)。製品の修正と検証は完了。利用中のサービスの置換、コミット、push、PR、統合は実施していない。

## 設計と所有

カードの取得結果とエラーは既存 ViewModel の入口で確定する。View に token と適用結果を配線する案と比較し、二重の成功・失敗処理を減らす案を採用した。カード外の局所取得は既存の世代を保持する。二案は同一モデルの独立文脈であり、異なるモデルによる設計評価ではない。

通信・索引、投影・View 接続、native fixture の所有を分離した。検証は書込み担当と分け、全体がそろってから作業全体を一度レビューする。

## 修正内容

消えた取得対象を HTTP 400 に変換していた通信境界を 404 に訂正し、本文取得の client で `notFound` に復元した。古いカーソルは構造版を範囲より先に検証し、カードのない作業にも独立した構造版を持たせた。

表示の成功と失敗は対象と取得世代で照合してから ViewModel で確定する。正常な消失は親セッションを確認し、現行表示へ有限回の再同期を行う。再同期中にさらに変わった場合は次の定期更新を待つ。旧要求が新しい表示や別対象のエラーを上書きすることも防ぐ。

文言からの推定、400 の一律握りつぶし、タスク名からの同一性推定、全文再取得や無限再試行は採用しなかった。不正要求の検出と既存の取得上限を維持しながら、意味が失われた最初の境界を直せるためである。

### 検証範囲と後片付け

macOS 専用の独立 lint・静的解析入口は未設定。実機 iPhone は対象外。既存のページ・容量上限の回帰も実行したが、実アプリで通信量の総計や計画中の要求回数の一般式の全組合せを計測したとは扱わない。速度向上も測定していない。

所有記録で検証プロセスの残存 0 件を確認した。使用済みの隔離アプリ・生成ソース・合成データはゴミ箱へ移し、再現・受入の証拠と未統合の作業ツリーを保持する。管理ビルドは両セッションを `finish` 済みで、保存期間の整理は共通ツールへ任せた。普段のアプリとサービスには触れていない。

## 残る導入制約

画面を更新しても既存サービスの bundle は切り替わらない。旧サービスの 400 は意味を識別できないため、修正保証は修正版同士に限る。実利用環境での解消は安全な時点のサービス切替と実測が別途必要。
