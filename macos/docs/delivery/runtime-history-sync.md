# 問題定義: 大きい会話で不要な状態計算をしない

## 解決したい問題

`torigonon-fix`を表示すると重く感じる。履歴を削らず、表示に使われない過去のコマンド解析を除く。既存の差分同期を重複実装しない。

## 現状（調査の根拠つき）

調査元の`.verification/torigonon-fix-slowness/`で採取した実アプリは画面1.14.3、実行サービス1.14.1だった。対象の保存履歴は3,273項目、4,812,806byte。これは2026-11-02の観測であり、修正後の値ではない。

開発元`913abe9a`の`SessionRuntimeClient`と`SessionRuntimeTransport`にはADR0224の差分同期が実装されている。`SessionRuntimeLauncher.connect`は稼働中サービスを維持し、旧サービスでは完全同期へ戻る。GUIの更新だけでは旧サービスは更新されない。通常の終了はセッションの停止も伴うため、稼働中のサービスをこの作業で無断終了しない。

追加の読み取りhandshakeでも、PID39692の`supportsSnapshotUpdates`が未対応と確認した。画面の版だけからの推測ではなく、接続先が完全同期を使うことを確認した。

基準`913abe9a`の変更前コードでは、`ChatRecap.deriveActivityState`と`summary`は最後のユーザー入力を探した後、そこからの履歴を前向きに処理していた。使うのは最新の候補だけだが、過去のコマンドも分類していた。`AgentActivityClassifier.state`と`RecapActivity.fromCommand`は先頭語だけを使うのにコマンド全文を分割していた。実アプリのsampleにもこれらの経路が現れた。sampleの重みを入力遅延の寄与率とは扱わない。

## 設計

データは既存の順序付き`[ChatItem]`のまま使う。状態は末尾から最初の該当項目を採る。ユーザー入力へ達したら前のターンを読まない。要約は最新のコマンドか有効なファイル変更を優先し、それが無い場合だけ最新の推論見出しを使う。空のファイル変更で要約探索を止めない。待機状態の優先と5秒の表示閾値を保つ。

コマンド分類では先頭の空白と先頭語だけを読む。要約の空コマンド判定は従来どおりFoundationの空白文字集合を使い、最初の非空白で止める。トークン境界には従来の`Character.isWhitespace`を使う。両者が異なるU+200Bも回帰で固定する。活動状態と要約は読み取り名の集合が異なるため、集合を統合しない。呼び出し側の契約は変えない。

同じ親モデルの別コンテキストで実行サービスと活動表示を調査した。比較した案は次のとおり。

| 案 | 判断 |
| --- | --- |
| 末尾から必要な候補だけ読む | 採用。結果を上書きする仕事を除け、状態の保持を増やさない。 |
| revisionごとに導出結果を保持する | 保留。復元とGUIローカル変更の失効管理が増え、現時点で必要とは確認できない。 |
| コマンドの全文分割だけを止める | 単独では不足。過去の全コマンド分類が残る。 |
| 差分同期を作り直す | 不採用。実装済み。旧サービスの置換はライフサイクルの問題として分ける。 |

異なるモデル系列による設計比較は未実施。最終差分は別コンテキストで独立レビューする。

## 成功基準（検証可能な形で）

- ユーザー入力の境界、状態と要約の優先順位、空の変更、nilコマンド、空白を含む分類を回帰テストで確認する。
- 既存の3,273項目相当の合成履歴を使い、変更前後で活動状態と要約が一致する。Releaseで交互比較できる同条件の計測を残す。単体の処理時間を画面や入力の改善率へ読み替えない。
- プロジェクトの標準品質ゲートを実行する。既存の差分同期の受入テストを隔離アプリで実行し、大履歴の表示と保存の一致を確認する。
- 実アプリの表示確認は隔離データで行い、ユーザー用アプリの再起動やサービス停止をしない。
