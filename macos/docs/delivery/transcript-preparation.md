# 表示する履歴だけを組み立てる

## 問題と現行コード

大きい会話の表示前処理を軽くする。[前段の修正](runtime-history-sync.md)と合わせて統合する。開始時の`ChatTranscriptView.transcriptStack`は全履歴をブロック配列に変えてから、予算内の末尾だけを選んでいた。さらに全ユーザー入力からIDのSetを作り、可視行の種類を判定していた。`ChatTranscriptGrouping.visibleSlice(from:blockLimit:)`も全ブロックを生成してから末尾を切り出していた。これらは今回の開始時コードで確認した事実で、画面遅延への寄与は未測定。

## 選ぶ形

既存の順序付き`[ChatItem]`と`ChatTranscriptSlice`を使う。履歴を逆順に1回走査して総ブロック数を数え、末尾の要求件数分だけを組み立てる。非表示のコマンド群の配列は作らない。表示するコマンド群は先頭IDを維持し、群全体を元の順序で渡す。

画面はその候補だけに既存の描画予算を適用する。候補より前の隠れ件数と、予算により除外する候補数を足して、表示する隠れ件数を保つ。ユーザー入力かどうかは可視ブロック自身で判断し、全入力IDのSetを作らない。

全ブロック数を正確に表示するため、軽い全件走査は残る。「履歴件数に依存しない処理」とは主張しない。本文の保持、キャッシュ、失効用revision、新しい依存は追加しない。スクロール位置に対する入力選択は同じ座標の優先順があるため、この修正では変更しない。

## 比較した案

| 案 | 判断 |
| --- | --- |
| 必要な末尾ブロックだけを実体化 | 採用候補。隠れた本文の配列生成を省き、既存の純関数とデータ形を維持できる。 |
| ビューごとに本文と全ブロックの1件メモを持つ | 保留。不変本文には効く可能性があるが、本文更新時の全件生成は残り、追加保持とコピーの費用が生じる。 |
| モデルのrevisionだけで再利用する | 棄却。既存の明示的なtranscript配列入力の契約を満たさない。 |

同じ親モデルの2コンテキストで両案を検討した。異なるモデル系列による比較は未実施。

## 守る表示契約

- 非LazyのVStack、表示予算の重み・最低件数・段階的拡張を保つ。
- コマンド群の先頭ID、群内の順序、全内容、正確な隠れ件数を保つ。
- 単一・グリッド、明示配列、過去メッセージの追加、群内へのジャンプとrevealを保つ。
- スクロール量やGeometryReaderの観測値を描画件数へ戻さない。

候補を末尾Rブロックに絞ってから予算を計算しても、各段階が見る末尾範囲は同じ。Rが既定段階より小さい場合も、最後のRによる制限が同じ結果になる。最低保証やreveal由来の要求も最後の候補数で制限されるため、全ブロック入力の結果を変えない。境界は既存テストと追加回帰で確かめる。

## 検証

変更前後のReleaseで実物のスライス処理を計測する。3,273項目、長い単独行列、全件が1コマンド群の対照を分け、戻り値・件数・ID・順序を検査する。関数の時間を入力遅延や画面全体の改善率とは扱わない。

既存のウィンドウ、描画予算、履歴追加、ジャンプの回帰を維持し、隠れた巨大群と先頭可視群、予算の拡張境界を追加する。標準品質ゲート、既存の画面外描画、隔離アプリの大履歴受入で確認する。利用中のReleaseと実行サービスは止めない。

設計は製品変更前に記した。製品2ファイルと既存テスト2ファイルへ実装・回帰を追加した。コミット・統合・配布は行わない。
