# 問題定義: Claude 使用量の誤表示修正と通知・定期取得の統合

## 解決したい問題

Claude の実際の残量と異なる「5時間 100%・週次 100%」が出る経路を直し、並列実行中・待機中・Phlox に Claude セッションがない場合にも使用量を更新する。通知を優先し、通知だけでは不足するときに 1 分間隔で取得を補う。

この文書は修正範囲・実装順・検証条件の記録。`feature/claude-usage-one-minute` で通知優先・1分補完・専用プロセス・期限切れの不明表示を実装した。未コミットで、稼働中のRelease版には未反映。検証の範囲と限界は末尾に記録する。

## 修正範囲と決定

### 1. 期限切れ・古いキャッシュによる 100% 誤表示を修正する

- Claude について、リセット時刻を過ぎたことだけを根拠に使用率 0% を作らない。期限切れの枠は数値表示と同期データから外す。有効な他の枠は維持し、両枠とも不明なら既存の「取得できません」表示・表示設定に従う。
- 最新の有効な値として受け取った使用率 0% は、正しい残量 100% として表示する。
- キャッシュの読み取り成功と、新しい使用量の観測を分ける。statusLine キャッシュは起動時・取得失敗時の補助表示に使い、読んだ時刻で鮮度や次回問い合わせ期限を延ばさない。期限切れ、非数値、将来の `ts`、時刻不明を新鮮なデータとして採用しない。
- キャッシュしかない場合は既存の失敗情報・補助文で古い値だと分かるようにする。レイアウトを作り直さない。Codex・Cursor の残量の扱いは今回変更しない。

### 2. 通知を表示までつなぐ

- `ClaudeChatClient` が通知の `unifiedWindows` を解析する。使用率の割合を 100 倍し、Unix 秒を `Date` に変換する。`get_usage` の百分率・ISO 文字列の解析とは区別する。
- 有限・非負の使用率と有効なリセット時刻を持つ枠だけ採用する。100% 超の使用率は内部値で保持し、既存の残量表示の範囲に収める。欠損枠を 0% にしない。
- `NormalizedChatEvent` に使用量更新を追加し、`ChatSessionViewModel` → セッション作成側のコールバック → `UsageMonitor` へ渡す。`UsageQuerying.fetchRateLimits()` の契約は維持する。
- セッションごとの通知を監視処理の Claude 用状態に集約する。受信だけで会話を running にしたり、応答完了・未読・費用・会話履歴保存を発生させたりしない。終了済み・再起動前のプロセスからの通知は採用しない。
- クライアント内部の再起動世代の判定は既存の `spawnGeneration` に任せる。監視処理側は、既存の問い合わせプロトコルを拡張せず、接続元の `sessionID`・通知購読の識別子・`UsageQuerying` をまとめる内部アダプターを持つ。登録解除した接続元と専用プロセスの旧インスタンスからの結果を排除する。

### 3. Claude の取得を 1 か所で調整する

- 起動時は 1 回問い合わせる。その後は枠ごとの最後の有効な通知・問い合わせ結果から 60 秒経過したら補完する。片方の枠だけ届き続けても、もう片方の更新を無期限に止めない。
- 次回期限に合わせて待機を再計算する。単に 60 秒ごとのタイマーで経過を判定して約 120 秒待たせる構成にはしない。Codex・Cursor の従来 5 分周期は維持する。
- 同時に実行する Claude の能動取得は全セッションを通じて 1 件まで。原則、開始時刻から 60 秒以内に次の `get_usage` を送らない。問い合わせ先の変更・プロセス再起動でもこの制限を引き継ぐ。
- 接続可能なチャットを 1 本選ぶ。失敗時に同じ周期で全セッションへ連続問い合わせせず、次の許可された試行で別の接続先を選ぶ。
- 問い合わせ開始時の枠ごとの状態番号と接続元アダプターの識別子を記録し、待っている間に新しい通知が届いた枠を古い問い合わせ結果で上書きしない。クライアントの内部世代を監視処理から読み取る前提にはしない。古いリセット期間へ戻さない。通知は整数秒、問い合わせは小数秒なので、同じ秒のリセットは同一期間として比較する。使用率を無条件に `max` で固定する方式は、正当な訂正を隠すため採用しない。
- 古いキャッシュを読んだだけでは補完成功にしない。CLI 自身の共有キャッシュの取得時刻は公開応答から確定できないため、Phlox の受信時刻をサーバー実測時刻と称さない。
- 失敗時は 120 → 240 → 480 → 900 秒の待機とし、以後は最大 900 秒。CLI が待機時間を返す場合はそれを下回らない。HTTP 情報が公開されない失敗にもこの待機を適用する。失敗を残量 100% として扱わない。
- `rate_limits_available=false`、空の枠、解釈不能な応答を補完成功にしない。返せる残量がないことを表示し、問い合わせを連打しない。
- 自動更新オフでも従来の起動時 1 回は維持し、その後の能動取得は止める。受信済みの通知による表示更新は継続する。
- 「Claude の使用量を取得する」がオフなら、起動時取得を含む問い合わせ・キャッシュ採用・通知の表示への採用を止め、専用プロセスを終了する。Claude 自体の会話や内部通知の送信は止めない。古い表示を新鮮な値として残さず、既存の取得無効状態を使う。この設定は「自動で更新する」より優先する。

### 4. セッションがないときの取得専用プロセスを追加する

- 問い合わせ可能なチャットがない場合、Phlox 所有の Claude Code を最大 1 本、必要になった時点で起動する。通常のチャットセッションや履歴として登録しない。
- ユーザー提案の常駐方式を採用し、チャットがなく自動更新が有効な間は起動した 1 本を維持する。約 467MiB という単発観測と長時間推移が未検証である点は、この採用の既知コストとして残す。
- 検証した stream-json / `--safe-mode` / `--no-session-persistence` / ツールなしの起動を基にする。送るのは制御リクエストだけで、`user` メッセージ・会話生成は送らない。認証は未改変の Claude Code に任せ、Phlox が認証トークンを読み出して直接 API を呼ぶ方式にはしない。
- 使用量の制御通信・解析・プロセス起動を `ClaudeAgentKit` に閉じ込める。既存のトランスポートと解析を再利用し、人間向け `/usage` テキストの解析は復活させない。
- 利用可能なチャットへ切り替えたとき、自動更新を止めたとき、Phlox 終了時は専用プロセスだけを終了する。終了中の応答を無効化し、終了待ちには上限を設ける。異常終了の再起動にも取得失敗の待機時間を適用し、再起動ループを作らない。
- アプリ終了は通常終了と既存のシグナル終了の両方へ接続する。現在の正常終了は `App/AppDelegate.swift:12–40`、シグナル終了は `App/PhloxApp.swift:510–526` が PTY の終了を待つ構成であり、専用プロセスを持つ場合はその所有ハンドルも既存の終了ガードの対象に加える。新しい OS 常駐サービスや別のシグナルハンドラーは追加しない。
- 同一の標準 Claude 認証を対象とする。異なる設定ディレクトリ・接続先が明示されたセッションは混ぜない。任意の複数アカウントを切り替える UI は作らない。

## 仮定 / 未知

実装時に確定した設計:

1. `rate_limit_info.unifiedWindows` を解析する。匿名化した通知形式を `ClaudeUsageNotificationTests` に固定した。使用率を持たない単一枠名だけの通知は更新を発生させない。
2. `UserDefaults.didChangeNotification` と設定画面の `onChange` から反映し、待機を取り消して再計算する。MainActor上で即時に結果採用を止め、専用プロセスの終了を開始する。同値設定の通知では初回取得を中断しない。接続一覧の変更はObservationで追跡する。
3. 自動更新オフの初回は、専用プロセスを起動→取得→成功・失敗にかかわらず終了する。その後の通知は採用するが能動取得はしない。通常終了とシグナル終了は専用所有actorへ到達する。

- 通知の実受信を確認したのは上記 CLI バージョン・モデル・認証環境だけ。旧 CLI、別モデル、API キー利用などで通知・各枠がない場合は、能動取得または不明表示へ退避する。
- CLI は直近 1 分の使用量を共有・再利用することがあり、`get_usage` 受信時刻だけではサーバーデータの実取得時刻を確定できない。Phlox の補完を 1 分にしても、全端末を含めた消費を常に 60 秒以内に表示する保証にはしない。
- 通知にサーバー観測時刻やアカウント ID がないため、複数セッションの任意の応答の新旧・外部からのログイン切り替えを完全に識別できるとは主張しない。既知の取得中更新・旧プロセス・古い期間は排除し、それ以上の保証には追加の情報が必要。
- `get_usage` は実験的 API。具体的な問い合わせ回数上限は公式資料で未確認。CLI が HTTP 429 や Retry-After を公開しない場合がある。
- 専用プロセスの長時間メモリ推移は未検証。約 467MiB は 1 回の観測であり、上限値ではない。

## 制約（技術・運用・期限）

- 2026-10-15 の実装指示に基づき本計画を実装する。コミット・dev へのマージには別途承認が必要。既存の未コミット変更は保全する。
- `.env*`、ユーザーの入力ソース、稼働中の Release・ユーザーの Claude セッションを変更・終了しない。自分が作った検証用プロセス・データだけを終了・清掃する。
- 直接 OAuth API を呼ぶために認証情報を抜き出さない。専用プロセスの認証も Claude Code の既存の仕組みを使う。
- 共通の再試行フレームワーク・永続データベース・OS の常駐サービスは追加しない。取得の状態管理は一つにし、試験で差し替える境界を必要な箇所に限る。

## スコープ外

- 他エージェントの取得方式・間隔変更、使用率と残量の表示方針の変更、画面全体の再デザイン。ただし今回の目的に含まれる「Claude の期限切れ枠へ架空の残量を出さず、不明として扱う」変更は対象とする。
- 複数 Claude アカウントの選択 UI・認証情報の管理・任意の別資格情報で動くセッションの集約。
- 人間向け `/usage` の画面・テキスト解析、Claude Code バイナリの改変、追加会話による常時監視、外部ターミナルへのフックのグローバル設置。
- リリース、配布、verify/main への取り込み。

## 既知リスク

- 通知と問い合わせの両方で同じ CLI の互換性に依存する。通知欠損・API 変更・取得失敗を不明表示と失敗情報で表し、100% へ置き換えない。
- 専用プロセスは取得がなくてもメモリを使う。チャットが利用可能な間は不要な専用プロセスを持たず、将来の最適化で都度起動との比較を行う。
- 今回の誤表示を発生させた瞬間のログはないため、期限切れキャッシュ経路が当該画像の原因だったとは未確定。修正後は取得元・データ時刻・期限切れ・失敗の理由を認証情報抜きで追えるようにする。
