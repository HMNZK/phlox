# 競合比較で判明したギャップの修正プラン（T1〜T14）

> **このドキュメントの役割**: Conductor / Superset との比較調査で判明した Phlox 側のギャップを、
> 優先度・根拠・受け入れ基準つきの実装タスク（T1〜T14）へ落とした計画。
> **書かないもの**: 競合の詳細な操作記録（→ `macos/docs/research/`）・実装後の現状仕様（→ `macos/docs/architecture/`）。

## 0. この計画の要点（平易な言葉で）

いま Phlox は「複数のエージェントを同時に走らせる」ことを売りにしているが、
**同時に走らせたときに互いのファイルを踏み合わないための土台が製品に入っていない**。
ユーザーが自分で `--dir` を用意する前提になっている。

さらに、変更差分の一覧は「プロジェクト単位」なので、
**どのセッションがどのファイルを変えたのかが分からない**。
14 セッション動かして「誰かが壊した」とき、犯人を特定する手段が製品内に無い。

この計画は、その土台（衝突検知 → 隔離 → セッション帰属のレビュー）を先に作り、
そのうえで git 操作・一覧性・細かな UX を足す、という順序で並べたものである。

- commit/push/PR を worktree 隔離と同列で先行させる根拠は無い。**共有 checkout の衝突を解決しない限り、git 操作を増やしても安全性は上がらない**。→ T7 を P3 へ後置した。
- 「要対応」への集約は、**状態検出の誤判定率を先に測る**べき。誤った通知はジャンプ UI を足すと運用負債になる。→ T5（計測）を T6（UI）の前段に置いた。
- 自動リネームは「足すだけ」ではない。誤命名・再現性・ユーザー編集名の保護・ブランチ連動の責任範囲を決める必要がある。→ T4 の受け入れ基準に入れた。

## 2. 優先順位とその根拠

| 優先度 | タスク | なぜこの順序か |
|---|---|---|
| **P0** | T1 衝突検知 / T2 worktree 隔離 | 並列実行という売り文句の土台。**ここが無いまま他を足すと、壊れ方が増えるだけ**。T1（検知＝可逆・低リスク）を先に出して現状の実害を可視化し、T2（隔離＝挙動変更）へ進む |
| **P1** | T3 セッション帰属のレビュー | T2 で「セッション＝作業ツリー」が確立して初めて、変更をセッションへ帰属させられる（F4 の現状はプロジェクト単位） |

## P0 — 並列実行の土台

### T1. 同一作業ディレクトリの衝突検知（規模: S / 依存: なし）

**目的**: いま実際に起きている「複数セッションが同じ作業ツリーを共有する」状態を、ユーザーに見える形で検知・警告する。挙動は変えない（可逆・低リスク）。

**現状**: F2 / F3。`isManagedDirectory == false` のプロジェクトでは全セッションが同じディレクトリを共有するが、検知も警告も無い。

**変更内容**:
- 稼働中セッションの解決済み作業ディレクトリ（F1 の結果）を正規化して集計し、**2 つ以上のアクティブセッションが同一ディレクトリを指している場合**を衝突として判定する。
- セッション一覧・セッションヘッダに警告バッジを出す。バッジから「同じディレクトリを使っているセッション」の一覧へ辿れる。
- 新規 spawn 時に衝突が発生する場合、spawn 前に警告を出す（ブロックはしない）。

**受け入れ基準**:
1. 同一 `directoryPath` のプロジェクトで 2 セッションを起動すると、両方に衝突警告が出る。
2. `workingDirectoryOverride` で別ディレクトリを与えたセッションは衝突判定に含まれない。
3. シンボリックリンク・末尾スラッシュ・大文字小文字差の違いで**同一ディレクトリを別物と誤判定しない**（正規化のユニットテスト）。
4. セッションが終了したら衝突判定から外れる。
5. 既存の spawn 経路の挙動は変わらない（ブロックしない）。

**主要ファイル**: `SessionSpawnService.swift` / `AgentLaunchPlanner.swift` / セッション一覧の View

---

### T2. git worktree のオプトイン生成（規模: M / 依存: T1）

**目的**: 「セッションごとに隔離された作業ツリー」を製品機能として提供する。既定は変えず**オプトイン**にする（既存ユーザーの挙動を壊さないため）。

**現状**: F6。worktree 生成は無く、ユーザーが `--dir` で用意する前提。

**変更内容**:
- プロジェクト設定に「セッションごとに git worktree を作る」トグルを追加（既定 off）。
- on のとき、spawn 時に `git worktree add <session-workspace> -b <branch>` 相当を実行し、その worktree を作業ディレクトリにする。
- セッション終了・削除時に worktree を後始末する（**未コミット変更があるときは削除せず残し、その旨を通知する**）。
- 対象リポジトリが git リポジトリでない場合・worktree 作成に失敗した場合は、明示エラーにして従来の挙動へフォールバックする（**黙って共有ツリーへ落とさない**）。

**受け入れ基準**:
1. トグル on で spawn したセッションは、`git worktree list` に現れる専用ディレクトリで動く。
2. 同一プロジェクトで 2 セッションを起動しても T1 の衝突警告が出ない。
3. トグル off の既存挙動が一切変わらない（回帰テスト）。
4. 未コミット変更のある worktree はセッション削除時に**削除されない**、かつその事実がユーザーに伝わる。
5. git リポジトリでないプロジェクトでトグル on にすると、spawn 前に明示エラーが出る（サイレントフォールバックしない）。
6. worktree 作成失敗（同名ブランチ既存等）がエラーとして表面化する。

**スコープ外**: `.env` コピー・依存インストール（`npm install` 等）・ポート割当の自動化。競合はこれらを持つが、Phlox の対象プロジェクトは多様で汎用化できないため本計画では扱わない。

**主要ファイル**: `AgentLaunchPlanner.swift` / `SessionSpawnService.swift` / `Project.swift` / プロジェクト設定 View

## P1 — レビューのセッション帰属

### T3. 変更一覧をセッションスコープにする（規模: S〜M / 依存: T2）

**目的**: 「このセッションが何を変えたか」を製品内で確認できるようにする。

**現状**: F4。変更一覧は `project.directoryURL` 固定＝プロジェクト単位。どのセッションの変更か分からない。

**変更内容**:
- `WorkingTreeService` に渡すリポジトリルートを、**選択中セッションの解決済み作業ディレクトリ**にする。
- T2 の worktree 隔離が有効なセッションでは、その worktree の diff＝そのセッションの変更になる。
- 共有ツリーのセッション（T2 off）では**セッション帰属が保証されないことを UI に明示**する（「このプロジェクトの全変更を表示しています」等）。帰属できないものを帰属できたように見せない。

**受け入れ基準**:
1. worktree 隔離セッションを選ぶと、そのセッションの worktree の変更だけが出る。
2. 別セッションへ切り替えると一覧が切り替わる。
3. 共有ツリーのセッションでは「セッション単位ではない」旨の注記が出る。
4. 既存の diff 表示・ファイル編集ドロワーの機能は維持される（`changes()` / `detail(for:)` / `fileContents` / `save`）。

**主要ファイル**: `DashboardView.swift:573` 周辺 / `WorkingTreeService.swift`

## P2 — 多セッション時の識別性

### T4. セッション名の自動リネーム（規模: S / 依存: なし）

**目的**: 花の名前（Daffodil / Azalea / Poppy）だけでは、10 個以上並んだときに識別できない。初回メッセージから内容の分かる名前を付ける。

**現状**: F7。仮名生成と手動リネームはあるが、自動リネームは無い。

**変更内容**:
- セッションの**初回ユーザーメッセージ**から短い要約名を生成し、仮名を置き換える。
- **ユーザーが手動でリネーム済みのセッションは上書きしない**。
- 生成に失敗した場合は仮名のままにする（エラーで止めない）。

**受け入れ基準**:
1. 初回メッセージ送信後、セッション名が内容を表す名前に変わる。
2. 手動リネーム済みのセッションは自動リネームで上書きされない（フラグで保護）。
3. 自動リネームは 1 セッションにつき 1 回だけ発火する（2 通目以降で再命名しない）。
4. 生成失敗時に仮名が保持され、エラーがユーザー操作を妨げない。
5. ブランチ名との連動は**行わない**（責任範囲を分ける。T2 のブランチ命名とは独立）。

**主要ファイル**: `DashboardViewModel.swift:782` 周辺

---

### T5. 完了判定（要対応状態）の精度計測（規模: S / 依存: なし）

**目的**: T6 の「要対応セッションへの集約」を作る前に、**現在の状態検出がどれくらい正しいかを測る**。誤検出が多いまま通知 UI を足すと運用負債になる（独立レビューの指摘）。

**変更内容**:
- 既存のセッション状態判定（待機中 / 実行中 / 要承認 / 完了）について、判定の根拠と遷移をログへ記録する仕組みを入れる。
- 実セッションで一定期間走らせ、誤検出（本当は動いているのに「要対応」／要対応なのに検出されない）の発生率を集計する。
- 集計結果をこのドキュメント（または `docs/delivery/`）へ記録し、**T6 へ進むかを判断する材料にする**。

**受け入れ基準**:
1. 状態遷移とその根拠がログから追える。
2. 誤検出率の集計手順が再現可能な形で残る。
3. 計測結果が記録され、T6 の可否判断に使える。

**注**: これは計測タスクであり、UI 変更を含まない。結果次第で T6 の設計が変わる。

---

### T6. 「要対応」セッションの集約とジャンプ（規模: M / 依存: T5）

**目的**: 多数セッションの中から「いま人間の対応を待っているもの」へ即座に辿り着けるようにする。

**現状**: `2/14` のカウント表示と状態ドットのみ。フィルタもジャンプも無い。

**変更内容**:
- 「要対応のみ表示」フィルタ。
- 次 / 前の要対応セッションへ移動するキーボードショートカット。
- カウント表示からのジャンプ。

**受け入れ基準**:
1. フィルタ on で要対応セッションだけが一覧に残る。
2. ショートカットで要対応セッションを巡回でき、末尾で先頭へ戻る。
3. 要対応が 0 件のときショートカットが無害に何もしない。
4. T5 の計測で誤検出率が許容範囲であることが確認できている。

## P3 — git ワークフローと正直な機能表示

### T7. commit / push / PR 作成（規模: L / 依存: T2, T3）

**目的**: レビューから git 操作までを製品内で完結させる。

**現状**: F5。ブランチ一覧と checkout はあるが、commit / push / PR / merge は無い。

**変更内容**:
- 変更一覧（T3）からステージ選択 → コミットメッセージ入力 → commit。
- リモートがある場合の push。
- PR 作成（`gh` CLI があれば利用。無ければ push までで止め、その旨を表示する）。

**受け入れ基準**:
1. T3 の変更一覧から選択したファイルだけをコミットできる。
2. コミットメッセージが空のときコミットできない。
3. リモート未設定のリポジトリで push ボタンが無効化され、理由が表示される。
4. `gh` 不在時に PR 作成が「利用不可」と明示される（黙って失敗しない）。
5. 失敗した git コマンドの stderr がユーザーに見える形で提示される（握りつぶさない）。
6. **merge はスコープ外**（衝突解消 UI が必要で規模が別）。

### T8. モバイル承認の対応状況を明示する（規模: S / 依存: なし）

**目的**: F9 の限定（Codex の構造化承認のみ対応）が UI 上どこにも書かれておらず、「モバイルから全部承認できる」と誤解される。正直に出す。

**変更内容**:
- モバイル側・設定画面で、承認のリモート操作が **Codex セッションのみ対応**であることを明示する。
- Claude / Cursor セッションでは、モバイルから承認できないことと、その理由（PTY 承認は構造化されていない）を短く示す。

**受け入れ基準**:
1. Claude / Cursor セッションをモバイルで開いたとき、承認不可であることが分かる。
2. 設定画面に対応エージェントの限定が記載される。
3. 誤解を招く「承認できる」表現が残っていない。

## 3. スコープ外（この計画では扱わない）

意図的に外したもの。理由つきで明示する。

| 項目 | 理由 |
|---|---|
| チーム / SSO / 組織設定 | 単独利用の設計思想と別軸。競合の Teams プランに相当し、規模が桁違い |
| 定期実行（スケジューリング） | 独立した大機能。本計画の目的（並列実行の安全性）と関係しない |
| エージェント数のレース制御 | `SpawnPolicy` が既にレート・深さを持つ。本計画の衝突とは別問題 |
| クラウド実行 | インフラを伴う。OSS ローカル実行という設計思想と衝突する |
| worktree セットアップの完全自動化（`.env` コピー・依存インストール・ポート割当） | 対象プロジェクトが多様で汎用化できない。T2 は worktree 生成までに限定 |
| merge / 衝突解消 UI | T7 のスコープ外。衝突解消は独立した規模の機能 |
| コンテキスト残量表示 | **F8 により実装済み**。当初挙げたが撤回した |
