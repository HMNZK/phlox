# Phloxのセッションを画面プロセスから独立させる

## 目的

Phloxの画面を終了、更新、再起動しても、既に動いているセッションの処理を継続する。起動後のPhloxは継続中の実行へ接続して状態を表示し、入力、承認、停止を行える。分離実装は作業ブランチに存在し、隔離した署名済みDebugアプリで終了・再接続・アプリパス差し替えを検証した。実Claude/Codexを使ったDebug版間のSparkleインストールと再接続も手元で確認した。

## 実行の所有者

同じユーザーと保存先ごとに共通の常駐実行プロセスを置く。常駐側が実行、入出力、承認と質問の保留状態、実行中エージェントが使うhookと操作APIを所有する。Phloxの画面は表示と操作のクライアントになる。画面と常駐側が同じセッションの状態や作業用ディレクトリを別々に変更する状態を作らない。

## 満たす条件

1. 画面プロセスの正常終了と予期しない終了で実行を停止しない。
2. 画面不在でも出力を読み、実行状態を更新する。新設する保留キューと出力保持量には上限を設ける。
3. 再接続で現在状態と続きの出力を取得する。端末の画面と入力モードを復元する方式は、実際の端末応答を検証して選ぶ。
4. 再接続で未解決の承認と質問を取得し、同じ要求へ一度だけ応答する。画面不在を自動承認や自動拒否の理由にしない。
5. 起動済みエージェントのhookと操作API、認証情報、使用中の補助資材は画面を閉じても有効に保つ。
6. 接続失敗と実行不存在を区別する。継続実行を現在の孤児回収と再生成の処理へ流さず、二重起動を防ぐ。
7. 画面の切断、実行の停止、削除と資材の後始末を別の操作として扱う。
8. 常駐側は同じユーザー権限で動く。接続と新規保存物にアクセス制限を設け、子エージェントの資格情報を常駐側全体の管理権限へ拡張しない。
9. 更新後も稼働中の常駐側と操作できる互換性を保つ。非互換の更新は実行中に適用しない。後から呼ぶ補助スクリプト等の資材も維持する。

## 対象外

常駐プロセス自身のクラッシュと更新をまたぐ無停止保証、OS再起動とログアウト中の実行、旧方式で稼働中のプロセスの無停止移送、全履歴保存の全面改修は含めない。段階導入する場合は対応する実行方式を明示し、未対応の方式を独立化済みと扱わない。

送信の受理とエージェントの処理完了を分ける。停止は送信準備の取消しも含み、取消し済みの送信が後からエージェントを起動しないよう、各クライアントの送信入口と承認待ち後でも取消しを確認する。受理後に送信に失敗した入力は、再接続後も回収できる状態で保持する。

## 受入検証

対応対象の各実行方式で、画面の正常終了、予期しない終了、互換版への更新と再接続を隔離環境で確認する。終了前後の実行PIDと作業の進行、無人時の出力、再接続後の入力、承認と質問、必要なhookと操作API、明示停止と削除を検査する。コンパイル成功だけを実行継続の証拠としない。XCUITestは使わない。

## 実装方針と現在の状態

同じ署名済みアプリに画面を作らない実行モードを設ける。既存の実行用モデルと承認の保留処理を常駐側で再利用し、画面側のモデルには副作用のない生成経路、状態の適用、操作の送信を加える。画面側では起動時のPID回収や再生成を行わない。全還元処理の抽出、新しい永続ジャーナル、ログイン時の自動起動は今回の初期条件に含めない。

保存先ごとの排他ロックとアクセス制限された接続情報を使い、実行世代とプロトコル版を接続時に照合する。端末の解析と端末からの応答は常駐側だけが行う。GUIへの状態転送は遅いGUIのために無制限に蓄積しない。送信や削除の結果が不明な場合は新しい操作として自動再送しない。

画面側は`DesktopCompositionRoot`、実行側は`SessionRuntimeHost`が組み立てる。同じ署名済みアプリを内容のハッシュごとに保存し、`--session-runtime`で独立したプロセスとして起動する。実行側では画面を生成せず、更新処理も起動しない。画面の通常終了は接続の切断だけを行い、セッションの明示停止は操作として実行側へ送る。プロジェクトの補助シェルタブは従来どおり画面側の所有である。

状態取得と停止・承認などの操作には、通常の送信と別の待機枠を設ける。操作結果を識別子で保持し、同じ操作の再送は再実行しない。長い最初の送信も実行側で保持して、画面には受理を先に返す。失敗した本文と画像は識別子で回収し、同じ状態取得で入力欄を繰り返し上書きしない。

端末の解析は実行側だけで行い、画面へはセル・カーソル・入力モード・画像の参照を送る。画像は実行世代ごとの非公開保存先に置き、画面の状態は取得開始から35秒で失効させる。不要画像には40秒の保持期間を設ける。転送上限は画面状態64MiB、操作要求160MiB、操作結果128MiB、端末は最大1024列・1024行、4000履歴行とする。上限超過を黙って欠落させず、接続失敗として表示する。

署名付きDebugアプリのビルド、関連パッケージの標準テスト、登録した受入テスト`macos/scripts/tests/session-runtime-lifecycle.test.py`は手元で実行した。受入テストはCLIをフェイクに置換し、PTY、Claude/Codex/Cursorの構造化チャットについて、画面の正常終了・強制終了・アプリの別パスへの差し替え中も同じ実行PIDと出力が続くこと、再接続後の入力・承認・質問・hook・操作API・明示停止を確認する。通常の再起動後に画面へ実行側の状態が表示されることもAXで確認した。別の手元試行ではCUAで承認と質問回答を実際に操作し、それぞれ一度だけ子へ届くことを確認した。

検証アプリは固有のbundle ID・保存先・defaults suite・ポートを使う。初期試行の利用状況DBの隔離不足は、Foundationのホームディレクトリが検証用の`CFFIXED_USER_HOME`へ変わることを実走してから修正した。初期試行で実利用状況DBを読んだか、外部通信が発生したかは未確認。現在の受入手順は空の検証用ホームと明示的に無効にしたAPNs資格情報を使い、秘密トークンを検証ログへ出さない。

追加した60秒の連続状態取得では、一部接続のHTTP応答が20秒以内に返らない不具合が再現した。接続ごとの記録により、開始済み接続の準備完了通知が旧ハンドラへ配送予約され、新しい待機側へ届かない競合を特定した。準備完了を観測するハンドラを接続開始前に登録する共通APIへ変更し、関連サーバーも同じ順序を使う。通知の配送予約を再現する回帰テストと実接続テストを追加した。

診断コードを除去した最終版で、4方式を実行中に60秒の連続取得を行い、状態とアプリ状態を各575回、合計1150回取得した。タイムアウトは0件。混雑応答503は7回あり、GETの有界再試行で回復した。その後の正常終了・強制終了・パス差し替え・再接続・同じ承認と質問への一度だけの応答・明示停止も通った。1回の受入試験は79.643秒で成功し、所有する検証プロセスの残存は0件。手元の実行記録は作業内`.verification/independent-session-runtime/verification-results.md`に保存する。常駐プロセス自身の再起動をまたぐ継続は対象外。

再実行は、固有bundle IDでビルドした検証アプリを使い、次の登録済みテストを実行する。実行先は未使用の作業専用ディレクトリを指定する。

```sh
~/.agents/scripts/compact-test runtime-lifecycle \
  python3 -B macos/scripts/tests/session-runtime-lifecycle.test.py \
  --app <検証用Phlox.appの絶対パス> \
  --work-dir <worktree>/.verification/<一意の作業名> \
  --include-additional-structured --snapshot-soak-seconds 60
```

更新候補は、appcastに明示された対応プロトコル範囲で受入を判定する。対応範囲が不明な候補も延期する。この判定を採用する前に既に準備済みだった外部更新処理は保証対象外とする。旧方式の稼働プロセスの移送と同様に、最初の導入時の移行条件として区別する。

追加の手元検証では、実Claude Code 2.1.304とCodex CLI 0.164.0の2セッションで処理を走らせたまま、Sparkleによる署名付きDebug版900001→900002の検出・ダウンロード・インストール・再起動を実行した。常駐側と両CLIのPID、実行世代、処理の進行を維持し、更新後の追加質問にも両モデルが更新前の会話内容を保持して回答した。作業内unittestは1件185.815秒で成功し、GUIでも確認した。検査はリポジトリ標準テストには未登録。記録は`.verification/real-cli-sparkle-20261023/results.md`。同じ製品実装の版番号を変えたDebug版間の検証であり、公開Release配信、notarization、異なるプロトコル版、差分更新は未検証。

## 制限

失われたworktreeを再作成するGUI確認の中継は未実装で、常駐側はその要求を拒否して失敗を記録する。プロジェクトの補助シェルタブ、OS再起動、ログアウト、常駐プロセス自身の停止をまたぐ継続は対象外。

macOSでバックグラウンド実行を明示的に停止・禁止された場合も継続を保証しない。OSの設定をアプリから変更したり、停止を回避したりしない。今回の方式はアプリからの独立プロセス起動であり、`SMAppService`によるサービス登録は行わない。[Appleのバックグラウンドプロセス管理](https://developer.apple.com/documentation/appkit/managing-ongoing-background-processes-in-your-mac)を参照。
